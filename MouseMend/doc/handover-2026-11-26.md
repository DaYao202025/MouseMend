## 0. 一句话总结

今天把「长按标题栏 → 松开 → 移动鼠标，窗口还跟着走」这个反复出现的问题**定位到根因并修掉**，
发布 **v2.3.0**；同时把自测/追踪版拆成独立子项目 `tools/MouseMendTrace`。

**关键结论：这不是一个 bug，是三个独立缺陷叠在同一条「松手」路径上。**
前两次修复（`||`→`&&`、加 `system_down`）都只碰到了症状，因为真正让按钮停在"按下"的
是**补发逻辑本身替用户按下了一次**。

## 1. 现象与判据

用户描述（原话整理）：

1. 长按我们窗口的标题栏约 1 秒；
2. 松开左键；
3. 移动鼠标 —— **窗口继续跟着走**；
4. 再点一下，窗口才停住。

这个组合只有一个解释：**系统认为左键仍然是按下的**。所有排查都围绕这一句展开。

判据（后来写进追踪日志）：`GetAsyncKeyState(VK_LBUTTON)` 在松手后仍为按下，
且前台窗口矩形继续变化。

## 2. 三个根因（按发现顺序）

### 2.1 被扣住的松手可能永远补不回来（P0）

- **机制**：推迟补发依赖一个 15 ms `WM_TIMER`。这个定时器为了省电，在没有待办时会
  `KillTimer` 自己，但**没有**调用 `debounce_set_defer_available(false)`。
  引擎那边只看这个开关，于是"能推迟"仍为真、定时器却已不存在 → 松手被吞、永远不补发。
- **为什么长按必中**：定时器在**按下后 15 ms** 就自停了，任何长于一个 tick 的拖拽，
  松手时定时器早就没了。
- **证据**：自建探针用真实 `debouncer.c` + 复刻 `main.c` 的定时器结构，输出
  `UP injected: 0`、`deferral still pending: YES`；把定时器在松手前重新武装，则 `UP injected: 1`。
- **修法**：
  - `main.c`：在**判定之前**对非注入的松手调 `EnsureSmartDragTimer()`；
  - `main.c`：自停分支补 `debounce_set_defer_available(..., false)`；
  - 让「能推迟」与「有定时器」永远同真同假。

### 2.2 重放按下 = 替用户把按钮按住（真正的元凶）

- **机制**：扣住一次松手期间，如果又来一个「按下」，旧代码（`deferred_release_take`）
  会把它吞掉，再让定时器补发 **UP + DOWN**。
  对磨损开关来说，那个「按下」**就是抖动本身**；一旦它后面没有对应的松开，
  系统就被重新按住 → 窗口一直跟手，直到下一次点击。
- **证据**（用户机器 `trace-20261126-095643.log`）：反复出现同一段三连

  ```
  up   verdict=deferred-release      ← 松手被吞
  down verdict=passed-flushed        ← 0.4ms 后一个「按下」
  up/down verdict=ignored-injected   ← 我们注入的 UP + DOWN  ★
  ```

  同一份日志里窗口矩形 `531,185 → 230,214 → 193,269 → 151,274 → 149,307`，证明确实在拖。
- **修法**：删除 `deferred_release_take()` 与「取走 + 重放」整段触发；
  推迟期间收到按下 → `BLOCK_DEFERRING` 拦掉，**不清 `isDeferringRelease`**，
  定时器只补发**一个 UP**。没有任何路径会注入 DOWN。

### 2.3 扣留本身对这颗开关是纯成本

- **测量**：7 次扣留 → 松手到真正送达系统：`22.3 / 79.0 / 78.5 / 26.1 / 24.6 / 26.1 / 25.6 ms`。
  79 ms 那两次是 **`WM_TIMER` 在鼠标持续移动时被饿住**（它是低优先级合成消息）。
- **判断**：这颗开关的抖动**只发生在松手瞬间**（7/7 次松手后 0.3–0.8 ms 内必跟一个被拦的按下），
  而「扣留」是为了挡**拖拽中途**的抖动 —— 对这台机器买不到任何东西。
- **修法**：`Release Delay` 默认 **20 → 0**，且 **0 表示"从不推迟"**（不是"推迟 0ms"）。
  菜单新增「关闭」档，保留 20 / 40 / 80 给真的会在拖拽中途抖的开关。
- **迁移**：注册表里存的 `50` 与 `20` 都是旧默认值，启动时一律落到 0；`40 / 80` 视为用户选择，保留。

### 2.4 同一天更早的一批（审计修复，与粘连无关）

这些在今天的粘连排查之前就已经改完并验证，避免后来人以为它们还没做：

| 项 | 改动 |
|---|---|
| 拦截日志写入 | 从"每条一次 open/close"改为**一次打开批量写**（`block_log_write_many`），减少钩子线程上的磁盘操作 |
| 诊断包/崩溃包 | 先写 `.part`，完成后再 `MoveFileEx` 原子改名，杜绝"打不开但占着名额"的半成品 |

### 2.5 顺带：2.0.0 为什么不粘

2.0.0（`9472819`）的 `debouncer.c:180` 在钩子回调里**直接** `force=true` 补发，
延迟约 **0.5 ms**。`b79af5c`（11-25）为修 `SendInput` 自等待死锁把这步交给定时器，
延迟变成 **20–80 ms**。**同一个功能，差了两个数量级** —— 这就是"以前不会，现在会"。

## 3. 现在的行为契约（改代码前务必遵守）

1. **任何情况下都不得替用户「按下」按钮。** 我们只允许注入 UP。
2. **系统认为按着时，绝不允许吞掉松手。** 由 `system_down` 把关。
3. **允许推迟，但"能推迟"必须与"定时器活着"同时成立。**
4. **默认不推迟。** `releaseDelayMs == 0` 时判据直接跳过。
5. **钩子回调只做 O(1) 内存操作**：不加锁、不分配、不读盘、不查进程、不 `SendInput`。
6. **不要用 `WM_TIMER` 表达精确延迟**（会被鼠标消息饿住）。

对应的单测已经锁住 1–4：`tests/test_smart_drag.c`、`tests/test_core.c`。

## 5. 自测版（排查问题的第一工具）

```
构建：  msbuild MouseMend.sln /p:Configuration=Release /p:Platform=x64
产物：  tools\bin\x64\Release\MouseMendTrace-x64.exe
运行：  MouseMendTrace-x64.exe --trace
日志：  %TEMP%\MouseMend-trace\trace-YYYYMMDD-HHMMSS.log
```

**与正式版的关系**：同一套源码，唯一区别是定义了 `MOUSEMEND_TRACE`。
正式版 `bin\...\MouseMend-x64.exe` 里**连 `MouseMend-trace` 这个字符串都不存在**
（发布前用字符串检查守住，见 §7）。

**规矩：自测版只用于内部复现，绝不外发。**

日志格式（一行一条，制表宽对齐）：

```
E <µs> left down pos=  x,   y verdict=<判定> sw=<吞掉> inj=<注入>
         | lbtn=<事件后系统按键态> cap=<捕获窗口> fg=<前台窗口> hit=<命中窗口> fgrect=l,t,w,h
M <µs> pos=x,y lbtn=<0/1> cap=... fg=... rect=l,t,w,h      ← 10 ms 采样
I <µs> seq=U|D count=n delivered=0/1                        ← 我们自己的注入
L <µs> hook-install|timer-arm|timer-stop|app-start|app-stop
```

**怎么读**：找 `deferred-release` 后面有没有 `I ... seq=D`（有 = 又在替用户按下）；
看 `M` 行里 `lbtn=0` 而 `rect` 仍在变（= 松手后窗口仍在移动）。

**最小复现步骤（约 10 秒）**：

1. 运行 `tools\bin\x64\Release\MouseMendTrace-x64.exe --trace`，等体检窗口出现；
2. 按住**它的标题栏**约 1 秒；
3. 松开后立刻移动鼠标，观察窗口是否还跟着；
4. 从托盘退出（不要强杀，强杀最多丢最后 200 ms 的记录），然后读最新日志。

## 9. 下一步需求（已于同日实施，见 §14）

> 状态更正：本节两项**已经实施并验证**，详细记录见文末 §14。以下原文保留，作为当初的需求描述。

### 9.1 自学习模式（独立线程）

- **学什么**：每个按键的「抖动间隔分布」，把阈值定在实测分位数之上一点。
  只调**参数**，不调**逻辑**；必须有上下限、可回滚、可在体检窗口里解释清楚。
- **线程模型**：
  ```
  钩子线程：只往无锁计数器 +1
  学习线程：每几秒汇总 → 原子发布建议阈值
  钩子线程：读一个原子 int
  ```
  **钩子永远不等待学习线程。**
- **纪律**：只在一次手势结束时换阈值；每个调整都要在界面上能看见依据。

### 9.2 白/黑名单（排除游戏/指定程序）

- **绝不**在钩子里 `OpenProcess` / `QueryFullProcessImageName`。
- 前台窗口变化时（低频）解析一次 exe 名 → 写进缓存（PID + 是否排除）；
  钩子只比较缓存里的 PID，命中直接早退，连引擎都不进。
- 按 **exe 名**匹配，不靠窗口标题；另外提供「临时暂停 5 分钟」作为兜底。

### 9.3 共同地基

两者都需要：**「当前上下文是否要介入」的廉价判断** + **钩子 → 工作线程的无锁通道**。
建议先落在 `src/core/context_filter.c`、`src/core/learning.c`（纯逻辑、可单测），
先在 `tools/MouseMendTrace` 里验证不拖慢钩子，再进正式版。

## 10. 今天的坑（别人会再踩）

1. **`WM_TIMER` 不是定时器**：它是低优先级合成消息，鼠标一直动就不派发。
   实测：拖动窗口的模态循环里它照常派发（800 ms 内 58 次），但**光标持续移动时会饿死**。
2. **"注入成功" ≠ "系统收到"**：真正要看的是 `GetAsyncKeyState` 与前台窗口矩形。
3. **`SendInput` 在钩子回调里会自等待**，整机卡死 —— 这是所有注入必须离开钩子回调的原因。
4. **用 `SendInput` 造输入测不了这条链路**：产品故意忽略 `is_injected` 事件，
   `stuck_key.ps1` 只能验证"注入输入原样通过"，验证不了扣留。
5. **别用计数判断按键状态**：Windows 的按键是布尔状态，连续两个 DOWN 仍是一个"按下"。
   我第一版穷举器就按次数算，误报 2685 例。
6. **构建产物的文件大小有延迟**：`Get-ChildItem` 可能读到旧的目录项，
   判断日志是否在写要看内容，不要只看 `Length`。
7. **截屏别用屏幕拷贝**：`SetForegroundWindow` 被前台锁拒绝后抓到的是别的窗口，
   要用 `PrintWindow`。

2. **`IsHookActive()` 假阳性**。`WatchdogState` 新增 `suspecting`（sticky，闲窗不清除，只有钩子真正上报事件或恢复后重新 init 才清）；`IsHookActive()` 同时要求 `hook_watchdog_is_healthy()`。托盘菜单、悬浮提示、体检窗口、诊断报告四处共用这一个入口。
3. **长路径静默失败**。新增 `SUPPORT_PATH_CHARS 1024` / `BLOCK_LOG_PATH_CHARS 1024` / `APP_SNAPSHOT_LOG_DIR_SIZE 1024`；诊断包、崩溃包、挂起包、拦截日志、日志路径的缓冲统一放大，大数组改 static（崩溃栈不可靠）。`build_candidates` 复用单个 scratch 并通过 `failures` 输出失败次数，`report.txt` 新增 `path_fail : N`。

## 15. 托盘菜单重构 + 白/黑名单模式（同日实施）

完整方案与三轮评审记录在 `doc/design-tray-menu-modes.md`。**动菜单或名单前先读它。**

### 15.1 菜单结构（一级净增 2 行）

```
[状态] [统计] / 7 个按键子菜单 / [禁用全部] [智能拖拽]
[自学习模式 ▸] [白名单模式 ▸ (N)] [黑名单模式 ▸ (N)] [清除统计]
[预设 ▸] [高级 ▸（含开机自启）] [语言 ▸] / [关于] [设置] [退出]
```

- 「开机自启」从一级移进「高级」；「高级」里原有的学习三项已删除（搬到自学习子菜单）。
- **`IDM_TOGGLE_LEARNING(+81)` / `IDM_ADOPT_LEARNING(+82)` 的 `WM_COMMAND` 分支必须保留**，
  只搬菜单项不搬 ID —— e2e 是按 ID 直接 `PostMessage` 的。

### 15.2 三模式（互斥枚举，不是两个开关）

```c
typedef enum { CONTEXT_MODE_ALL = 0, CONTEXT_MODE_WHITELIST, CONTEXT_MODE_BLACKLIST, CONTEXT_MODE_COUNT } ContextMode;
```

`context_mode_suppresses(mode, in_white, in_black)` 的返回值是**「是否放行」**：

| 模式 | 白名单内 | 黑名单内 | 其他 |
|---|---|---|---|
| ALL | —— | —— | 拦截 |
| WHITELIST | 拦截 | 拦截（防御） | 放行 |
| BLACKLIST | 放行 | 放行 | 拦截 |

读取 `ContextMode` 时校验 `< CONTEXT_MODE_COUNT`，越界回落 ALL（宁可多拦）。

### 15.3 数据与线程

- **单一真源**：名单只在 `ContextFilter.policy` 里，`Preferences` 不复制（避免两份漂移）。
  持久化独立成 `src/core/context_store.{c,h}`，由 `main.c` 的 `SaveSink` 额外调用。
- `ContextSnapshot`（钩子读）与 `ContextPolicy`（UI/轮询读写）分离；
  锁是 `ContextFilter` 顶层的 **`SRWLOCK`**，`context_filter_init` 里显式初始化，**永不删除**。
  policy 是纯 POD（无锁），可以随意 memset/复制 —— 这是 2026-11-26 崩溃的教训。
- 钩子只调 `context_filter_should_suppress(&filter->snap, ts)`，**函数体内不得出现 `AcquireSRWLock*`**。
- 名单修改经 `app_controller_{set_context_mode,add_context_path,remove_context_path,reset_context}`。

### 15.4 匹配规则（互斥的关键）

```c
// rule 两种形式：完整路径，或迁移产生的 "*\name"
bool context_path_matches(rule, full_path, file_name);
```

**查重和匹配必须调用同一个函数**：添加路径时先 `context_file_name_from_path` 提取文件名，
再在当前名单和另一名单里各查一次。这样 `*\game.exe` 与 `D:\Game\game.exe` 不可能共存。

### 15.5 持久化

| 键 | 类型 | 说明 |
|---|---|---|
| `ContextMode` | REG_DWORD | 0/1/2，越界回落 0 |
| `WhitelistExes` | REG_MULTI_SZ | 每项一个路径 |
| `BlacklistExes` | REG_MULTI_SZ | 同上 |
| `ContextMigrated` | REG_DWORD | 一次性迁移标记 |
| `ExcludedExes`（旧） | REG_SZ | 只读，迁移后保留不删 |

`REG_MULTI_SZ` 写：`cbData = (Σ(len+1) + 1) * 2`；N=0 写两个 NUL；**拒绝空条目**
（读侧遇空串即停，写入空条目会让其后条目全部静默丢失）。

### 15.6 迁移（实测通过）

旧 `ExcludedExes=explorer.exe` → `BlacklistExes=*\explorer.exe`，`ContextMode` 由 ALL 改 BLACKLIST。
用户升级后原有排除行为不变。迁移只跑一次（`ContextMigrated`），清空名单后重启不会回弹。

### 15.8 名单准入规则（同日补充）

| 级别 | 程序 | 理由 |
|---|---|---|
| **硬拒绝** `CONTEXT_ADD_RESERVED` | `System`、`Registry`、`smss.exe`、`csrss.exe`、`wininit.exe`、`winlogon.exe`、`services.exe`、`lsass.exe`、`svchost.exe` | 会话 0 进程永远不持有前台窗口，规则必然无效，但用户会以为生效了 |
| **软确认**（允许，先弹 `MB_YESNO`） | `explorer.exe`、`dwm.exe`、`sihost.exe`、`taskhostw.exe`、`StartMenuExperienceHost.exe`、`SearchHost.exe`、`SearchUI.exe`、`ShellExperienceHost.exe`、`ApplicationFrameHost.exe`、`TextInputHost.exe`、`conhost.exe`、`WindowsTerminal.exe` | 一条规则覆盖桌面 / 任务栏 / 全部 UWP 应用，影响面远大于名字暗示 |
| **不设限制** | 浏览器、Office、Adobe、AutoCAD、VS Code、微信/QQ、VLC、游戏 | 这些正是用户最常想加的目标，加任何限制都是阻碍 |

- 检查只在新添加时执行（`context_filter_add_path` 内）。
- **迁移来的旧规则直接写 `policy.blacklist.paths[]`，不经过 `add_path`，因此不受影响**——
  用户已有的 `*\explorer.exe` 继续生效，这是刻意的。
- 两张表是 `context_program_is_reserved()` / `context_program_is_shell()`，纯逻辑、可单测。

### 15.7 已知限制

- 菜单只显示文件名；同名不同路径的程序看起来一样，移除确认框里才显示完整路径。
- 把本程序改名后仍可被加入名单（按路径比较本进程 exe），属已知限制。
- 文件框是二段式（`WM_APP_ADD_EXE` → `WM_APP_ADD_EXE_FILE`），避免与菜单关闭时的
  `WM_NULL` 竞争、吞掉下一次托盘点击。**不要改成一步直接弹。**
- 设置窗口没有名单 UI（分层已留好，`context_filter_copy_policy` 可直接供以后使用）。

## 16. 打磨轮：7 个问题与修法（同日，未升版本）

用户报告「体检窗口开着调不出选择程序的窗口」，并要求把已有功能"调理顺畅"。通读新功能后
找出 7 个问题，其中 **4 个是"看起来能用、实际没生效"** 级别。

### 16.1 对话框被体检窗口盖住（用户报告的那个）

`GetOpenFileNameW` 的 owner 是隐藏托盘窗口，体检窗口的 owner 也是它——两者是**兄弟**，
Windows 把新对话框排在可见窗口**下面**。实测复现：文件框确实弹出（`选择要添加的程序`），
但 Z 序在体检窗口之后，用户只看到"没反应"。

修法：`UiDialogOwner()` 优先返回可见的体检窗口。实测 owner 从隐藏窗口变成体检窗口（`656910`），
体检窗口 `enabled=False`（正确的模态行为）。**所有**用户可见对话框（文件框、添加结果、移除确认、
shell 警告、恢复默认确认、关于、错误框、诊断包结果）统一走这个入口。

### 16.2 改名单要切窗口才生效（最严重）

`context_thread` 用 `pid == last_pid` 短路。用户在 chrome 里打开菜单把 chrome 加进黑名单，
回到 chrome 点击——`last_pid` 没变，不重算，仍然拦截。**规则生效依赖"切走再切回"**，
而用户不可能知道要这么做。

修法：`ContextFilter` 增加 `volatile LONG revision`，`add_path` / `remove_path` / `set_mode` /
`reset` 每次**真实**变更时 `InterlockedIncrement`；轮询线程比较 `pid + revision`，任一变化就重算。
轮询周期 2000 → **300 ms**（只在 pid/revision 变化时才 `OpenProcess`，空闲时几乎零成本）。

### 16.3 「采用全部学习建议」的可用条件算错

入口可用性按三个键样本的**总和** ≥ 32 判断，但门槛是**每键** 32。左 20 + 右 20 = 40 时总数够，
两个键却都没有建议——入口可点，点了什么也不发生。

修法：改判「至少一个键给出建议」（复用已有的 `any`），删掉 `total`。

### 16.4 子菜单「(未启用)」判断错

原来是 `policy->mode == CONTEXT_MODE_ALL` 才给两个子菜单加"未启用"。白名单生效
（`mode == WHITELIST`）时，黑名单子菜单**不显示**未启用，用户以为黑名单也在跑。

修法：按 `policy->mode != own_mode` 判断，每个子菜单只关心自己是不是当前模式。

### 16.5 空白名单没有任何警告

白名单模式下名单为空 = **所有程序都不拦截**，但子菜单只显示"尚未添加程序"，读起来像"还没配置"。
修法：白名单为空**且**处于白名单模式时，额外一行「名单为空：所有程序都不拦截」。

### 16.6 一键规则缺失（`IDM_EXCLUDE_CURRENT` 是悬空 ID）

`menu_ids.h` 早就定义了 `IDM_EXCLUDE_CURRENT`，`context_service_add_recent()` 也写好了，
但两处都没接线——死代码。用户要排除 `explorer.exe` 得自己去文件对话框里翻 `C:\Windows`。

修法：名单子菜单顶部加「不拦截 xxx.exe」/「只对 xxx.exe 生效」（复用 `IDM_EXCLUDE_CURRENT` +
新增 `IDM_ONLY_CURRENT`），名字来自轮询线程维护的 `recent_name`。**点击时如果当前是"全部程序"
模式，自动切到对应模式**——否则配置出来的规则不会生效，又是一次"点了没反应"。
`context_service_add_recent()` 删除（调用方直接读策略快照）。

### 16.7 暂停不可见、不可撤销

暂停 5 分钟后菜单项文字不变，用户不知道过滤已停；想恢复只能等 5 分钟或重启。
修法：菜单项按 `context_filter_is_paused()` 显示「暂停过滤 5 分钟」或「恢复过滤（已暂停）」，
同一个入口切换。

### 16.8 顺带的体验补强

- 采用建议后弹托盘气泡「已采用学习建议：左 40 ms, 右 55 ms」，并清空产生这些建议的样本
  （否则下一次手势结束会给出**同一份**建议，看起来像没生效）。
- 建议行显示样本数：`左 50 → 40 ms（32 样本）`。
- 名单改动文案从「最多 2 秒生效」改为「改动立即生效」（实际 300 ms）。

### 16.9 验证

四配置 Rebuild（含 `/analyze`）**0 error 0 warning**；单测 x64 **3162 / 0**、x86 **3162 / 0**
（较上一轮 3120 新增 42 条）；`audit_printf.py` 162 调用点 0 问题；
`e2e` / `diagnose` / `stuck_key` 各 0 failure。真机复现并验证：文件框 owner 从隐藏窗口变为
体检窗口、体检窗口被正确禁用、托盘菜单成功构建且无崩溃包。

### 16.10 新增契约（在 §3 六条与 §14.2 七条之上）

14. **名单/模式每一次真实变更都必须 `InterlockedIncrement(&filter->revision)`**；轮询线程按
    `pid + revision` 判断是否重算。**不能只按 pid 缓存**，否则"同一窗口内改名单"永远不生效。
15. **对话框 owner 必须走 `UiDialogOwner()`**：可见的体检窗口优先，否则隐藏托盘窗口。
    直接用 `g_app.hWnd` 会让对话框排在体检窗口**下面**。
16. **加名单的入口要顺手切模式**：当前是「全部程序」时，从子菜单添加规则等于配置了一条不生效的规则。

### 16.11 仍未做

见 §14.5（钩子开销实测、真实鼠标验收）。本轮**没有升版本、没有提交、没有发布**。

## 17. 自学习「一直样本不足」：三个缺陷叠在一起（同日）

用户报告菜单里自学习永远显示「样本不足」。查下来不是显示问题，是采样链路有三处独立错误。

### 17.1 采样条件依赖当前阈值（设计错误）

原来钩子只记 `reason == DEBOUNCE_REASON_BLOCK_THRESHOLD` 的按下——即**已经被阈值拦下的**。

后果是直方图描述的是**阈值**，不是**开关**：开关在 60 ms 上抖、阈值 50 ms 时，这些按下不被拦，
于是不入桶，于是 P80 永远 ≤ 50，建议永远升不上去。而「抖动比阈值长」恰恰是最需要建议的情况。
反过来阈值调低时同样学不到任何东西——自学习陷入「想学怎么调阈值，却必须先被阈值拦下」的死锁。

**修法**：采样窗口固定为 `SIGNAL_RING_SAMPLE_MAX_MS`（= 64 ms = 桶数），与阈值无关。
超过 64 ms 的间隔视为有意点击，不采（否则会把快速但故意的双击学成抖动）。
单测里加了 `SIGNAL_RING_SAMPLE_MAX_MS == SIGNAL_RING_BUCKET_COUNT` 断言：窗口若宽于桶范围，
超出的样本会被压进最后一桶，P80 会虚高。

### 17.2 等「空闲 300 ms」才重算（真 bug）

学习线程原来是：

```c
last != last_processed && signal_ring_gesture_complete(ring, i, now)
```

`gesture_complete` 要求距最后一次按下 ≥ 300 ms。用户为了测试会**连续抖动**，每次抖动都刷新
`last_activity_tick`，于是「手势」永远不结束，`advice` 永远不重算——样本在涨，菜单却一直是空的。
用户看到的「一直样本不足」多半就是这一条。

**修法**：删掉手势判定（连同 `last_activity_tick` / `note_activity` / `gesture_complete`），
线程改为「样本总数变化就重算」。建议值本来只是显示，中途刷新无害；一直不刷新才是问题。

顺带把钩子里的采样从 2 个原子操作降为 1 个（`InterlockedIncrement`），少一次 64 位写。

### 17.3 关闭学习时也显示「样本不足」（UX）

`if (!any)` 分支不区分「没开」和「没攒够」。学习默认关闭，所以绝大多数人第一眼看到的就是
「样本不足」，会以为程序在攒样本。

**修法**：关闭 → 「开启后开始采样」；开启但不足 → 「样本：左 N / 右 N / 中 N（需 32）」，
让进度可见。

### 17.4 时间精度：间隔 0 必须计入

`event.timestamp` 来自 `GetTickCount64()`，粒度约 **15.6 ms**。真实抖动（5–10 ms）经常和它前面的
松手落在**同一个 tick**，`elapsed_ms == 0`。

原条件 `elapsed_ms >= 1` 把这些样本全部丢掉——而它们恰恰是最确定的抖动。现在改用
`!decision.first_event` 排除首次按下，`elapsed == 0` 计入桶 1。

**这意味着学习给的是「档位建议」，不是毫秒级测量**：可用分辨率就是 15.6 ms。
文档和文案都不该承诺更高精度。

### 17.5 验证

四配置 Rebuild（含 `/analyze`）0 error 0 warning；单测 x64 **3148 / 0**、x86 **3148 / 0**
（净减 14 条：删掉 16 条手势判定断言，新增 2 条采样口径断言）；`audit_printf.py` 无问题；
`e2e` / `diagnose` 各 0 failure。

**验证盲区，必须说清**：`SendInput` 合成的按下带 `is_injected`，被采样条件排除，所以
**学习采样完全无法自动化测试**。单测验证的是「样本进来之后算法对不对」，采不采得到只能靠真机：
开着学习、让鼠标真的抖（或快速连点），菜单里的计数应该往上涨。

### 17.6 新增契约（第 17 条）

17. **学习的采样窗口必须与当前阈值解耦**。任何「先被拦下才记录」的写法都会让直方图
    描述阈值而不是开关，形成死锁。窗口上限也不得超过桶数。

## 18. 结构整理：命令分类 + 学习窄接口 + 能力自检（同日）

方案与两轮评审在 `doc/design-command-split-and-health.md`（v1 被否决 13 项 → v2 → 终审 3 项 → v3）。
按用户的「改动不影响其他功能 / 数据共用 / 模块化」三条要求做的，**零行为变更**。

### 18.1 四项改动

| 项 | 内容 |
|---|---|
| 菜单收窄 | 自学习子菜单改为 `键名 / 当前→建议 / 样本数` 三列。**建议值必须保留**——没有它用户无法判断「采用」会改成多少 |
| 命令分类 | 新增 `src/core/command_classify.c`（纯逻辑，可单测）；`WM_COMMAND` 拆成 `HandleMenuCommand` / `HandleThresholdCommand` / `HandleListCommand` / `HandleLearningCommand` 四个函数 |
| 学习窄接口 | `learning_service_start(..., LearningThresholdFn, void *user)`，不再持有 `DebounceManager *`；回调**不得加锁**（线程每 100 ms 问 7 次） |
| 能力自检 | 新增 `src/core/app_capabilities.c`：钩子 / 学习 / 名单 / 日志 四项，四态（关闭 / 正常 / 尚未观测 / 停摆），渲染进状态行 |

### 18.2 为什么没做物理拆分

`AppState` 是 `main.c` 内的 `static` 单例（`main.c:137/139`），18 个辅助函数直接读写它。
搬到新文件要么把它变成跨文件全局（耦合变隐蔽），要么参数化 18 个函数（1000+ 行）。
折中：**四个函数签名带 `AppState *app`、函数体也用 `app->`**，将来搬文件只是移动 + 改调用。

### 18.3 真机抓到的 bug（单测没抓到）

状态行第一次实测显示 `钩子! 学习? 名单✓ 日志✓` —— 钩子明明是正常的，却报「停摆」。

原因：符号表写成 `{✓,!,?,-}`，而枚举是 `DISABLED=0, OK=1, UNKNOWN=2, STALLED=3`，
**整体错位一位**。单测只断言「四个符号都出现过」，错位后四个符号依然都出现，所以全绿。

修法：符号表改为 `{-,✓,?,!}`，单测改为**逐状态校验「名字+符号」组合**。

**教训**：这类"枚举与查表顺序不一致"的错误，只有断言具体配对才能抓到，
断言"集合成员存在"等于没测。

### 18.4 验证

四配置 Rebuild（含 `/analyze`）0 error 0 warning；单测 x64 **3258 / 0**、x86 **3258 / 0**；
`e2e` / `diagnose` / `stuck_key` 各 0 failure；真机确认状态行渲染正确。

### 18.6 状态行：四个彩色标签 + 闪烁修复（已被 §19 取代，留作历史）

用户指出把四项能力拼在一条文本里"太简陋"，并要求分开控件、带底色、带悬停提示。

**闪烁根因（这是老问题，一直没修）**：`IDC_STATS` 早就有"只在文本变化时更新"的保护，
**`IDC_STATUS` 没有**——每 400 ms 无条件 `SetDlgItemTextW`，静态控件擦除 + 重绘整行。
现在加了 `last_status` 缓存比较。**以后任何定时刷新的控件都必须走这个模式。**

**布局**（`MouseMend.rc`，`IDD_SETTINGS` 第一行）：

| 控件 | 位置 | 宽 |
|---|---|---|
| `IDC_STATUS` | 8, 6 | 176 |
| `IDC_CAP_HOOK` | 190, 6 | 50 |
| `IDC_CAP_LEARN` | 246, 6 | 50 |
| `IDC_CAP_LIST` | 302, 6 | 50 |
| `IDC_CAP_LOG` | 358, 6 | 56 |

四个标签用 `CONTROL "Static", SS_CENTER | SS_CENTERIMAGE`——**不能用 `LTEXT`**，
它隐含 `SS_LEFT`，文字不会居中。

**自绘**：四个控件用 `SS_OWNERDRAW`，在 `WM_DRAWITEM` 里画。

- **为什么必须自绘**：`SS_CENTERIMAGE` 只对位图/图标生效，纯文本仍然贴在控件顶部，
  和右侧按钮对不齐——这是第一版看起来"歪"的真正原因。
- **怎么保证不位移**：文字用 `DrawText(..., DT_CENTER | DT_VCENTER | DT_SINGLELINE)`，
  位置全由 `DRAWITEMSTRUCT.rcItem` 决定，不手算 y 偏移。按 DPI 缩放时不会漂。
- **背景要自己擦**：owner-draw 控件不会自动擦除，`RoundRect` 也只覆盖圆角矩形内部，
  所以先 `FillRect` 整个 rc 为 `COLOR_BTNFACE`。
- **字体要自己选**：`WM_GETFONT` 拿到对话框字体存进 `window->base_font`，
  否则画出来是系统字体，和旁边控件不搭。
- **文字**用中文词而不是符号：`正常` / `待数据` / `未工作` / `未启用`。
  状态句同时缩短为「防护中 / 未防护」，否则一行放不下四个「名字 + 状态」。

| 状态 | 文字 | 底 | 字 | 边框 |
|---|---|---|---|---|
| 正常 | 正常 | `#E6F4EA` | `#137333` | `#7FBF8F` |
| 暂无数据 | 待数据 | `#FEF7E0` | `#8A6D00` | `#D9C06A` |
| 停摆 | 未工作 | `#FCE8E6` | `#C5221F` | `#E08B85` |
| 未启用 | 未启用 | `#E8E8E8` | `#9E9E9E` | `#C0C0C0` |

未启用用比窗口背景（`#F0F0F0`）略深的灰 + 灰边框，保留"格子"感但不抢眼。
边框比底色深一档，否则浅底上的圆角轮廓几乎看不见。

**画刷生命周期**：4 个 `HBRUSH` 存在 `SettingsWindow` 里，`ensure_cap_brushes` 幂等创建，
**刻意不删除**——窗口可关闭再打开，删了会变 use-after-free。

**悬停提示**：复用已有的 `window->tooltip`，`TTM_ADDTool` 四个，刷新时 `TTM_UPDATETIPTEXT`。
文本存在 `window->cap_tip[i]` 里，因为 **tooltip 只保存指针、不复制字符串**。

**首次绘制**：`last_caps` 初始化为 `0xFF`（非法状态），否则初始的 `DISABLED(0)` 会被当成
"已经画过且没变"，标签永远空白。

### 18.5 新增契约（第 18–20 条）

18. **`WM_COMMAND` 只做分发**，新菜单项加到对应的 `Handle*` 里，不要再往 `WindowProc` 里堆。
19. **命令的区间判定必须带上界**，且必须与 `menu_id_is_*` 解码函数的边界一致。
20. **能力自检的判据只能来自模块的公开查询函数**（`*_is_started` / `is_running`），
    不直接读别人的内部字段；查询函数必须在 memset-0 对象上安全返回 false。

## 19. 状态行改为「状态灯」色块条（同日）

用户提出新形态：五个无边框直角色块，观感像 LED 状态灯；鼠标滑过时悬停块加宽，直到
文字完整显示，移开回到五个方块。§18.6 的四个圆角 pill 已被这一版取代。

### 19.1 形态

| 元素 | 静止 | 悬停 |
|---|---|---|
| 宽度 | 正方形（= 控件高度，约 15 px @96 dpi） | 完整文字宽 + 2×5 px |
| 底色 | 该状态色 × **20%**（灯灭） | 该状态色 × **100%**（灯亮） |
| 文字 | 一个单字，**45% 白** | 完整文字（`钩子 正常`），100% 白 |
| 其余块 | 保持正方形 | 同时收回正方形 |

- 块 0 = 主状态：展开 `鼠标防护中` / `鼠标防护异常`，收起时单字「防」
- 块 1..4 = `钩` / `学` / `名` / `志`。中文取名字首字；英文用 `P` / `H` / `L` / `R` / `G`
  —— `Learn` 和 `List` 都是 L，必须换一个
- 无边框、直角。1 px 描边在 15 px 的块上吃掉 1/7 宽度，并让方形轮廓发糊

### 19.2 为什么是一个控件，不是五个

动画每帧都在改宽度。五个窗口就是每帧五次 `SetWindowPos`，而它们之间**一像素的偏差
看起来就是「永远对不齐」**——这正是用户反复说的「容易移位」。五个块在同一个客户区里
按累加 x 布局：前一块的右边界就是后一块的左边界，DPI 怎么变都不会错开。

### 19.3 动画：指数逼近，不是定时插值

```c
width += (target - width) * 0.14f;   // 每帧走完剩余距离的 14%
```

- 60 Hz 下约 **240 ms** 到 90%，读起来是渐变淡入，不是跳一下
- **从当前值逼近**，不是从起点重播：指针从第 1 块扫到第 4 块，中间每块都从自己当前位置
  改道，不会出现「新块从 0 开始」的闪跳
- 收敛判据：剩余 < 0.35 px 直接吸附到目标，否则会无限逼近、定时器永不降速
- 2 px 的块间隙不属于任何块，扫过时全部收起一瞬间——读起来是「一整条在动」
- 宽度和亮度共用同一个系数，所以变宽与变亮同时完成

### 19.4 文字交叉淡入

`DrawText` 没有 alpha，只能混色模拟：

- 单字：`ink = lerp(bg, white, 0.45 × (1 - reveal))`
- 完整文字：`ink = lerp(bg, white, 0.45 + 0.55 × reveal)`
- `reveal = clamp((level - 0.35) / 0.65)`

前 35% 只有单字在渐暗，之后完整文字渐亮。两者不会同时清晰，避免叠成一片糊。

### 19.5 踩到的坑：`SS_NOTIFY`

**`SS_OWNERDRAW` 的静态控件默认对鼠标透明**：`WM_NCHITTEST` 返回 `HTTRANSPARENT`，
鼠标消息直接穿透到对话框，控件自己的 `WM_MOUSEMOVE` 永远不来。

表现：子类化装上了（`SetWindowSubclass` 返回 TRUE）、`TrackMouseEvent` 也调了，
但所有块一直不动，只有状态颜色是对的。加调试标题才看出来——`strip_hover` 始终是 -1，
说明鼠标消息根本没到。

修法：资源里加 `SS_NOTIFY`。加完实测宽度 `21 → 58 → 74`（目标 75）、亮度 100%，
动画正常。

### 19.6 验证

四配置 Rebuild（含 `/analyze`）0 error 0 warning；单测 x64 / x86 **3327 / 0**；
`audit_printf.py` 164 调用点无问题；`e2e` / `diagnose` / `stuck_key` 各 0 failure。

真机截图三态：五个收起方块（`防钩学名志`，钩略亮为绿）、主块展开「鼠标防护中」、
钩子块展开「钩子 正常」且其余四块保持正方形。

### 19.7 已知取舍

静止时 20% 亮度的四种状态色**彼此差别很小**（深绿 / 深灰 / 暗黄 / 暗红在低亮度下人眼
分辨力弱）。这是用户明确接受的：方块里有单字，滑上去即可确认。
若以后有人反馈「看不出哪块不对」，第一优先级是把静止亮度提到 30–35%，**不是加边框**。

### 19.8 新增契约

21. **需要响应鼠标的 static 必须 `SS_NOTIFY`**，否则永远收不到 `WM_MOUSEMOVE`。
22. **宽度动画只允许「每帧逼近剩余距离」**，不允许 `x = start + (end-start) * progress`：
    后者在目标中途改变时会跳，前者不会。
23. **ease 必须在剩余 < 1 px 时吸附到目标**，否则定时器永远回不到 idle 速率。

## 20. 状态条定稿 + 全链路审计（同日，2.4.1）

§19 之后用户又提了四轮反馈，最终形态与 §19 有出入，**以本节为准**；§19.3 与 §19.8 的
第 22、23 条已被本节取代。

### 20.1 最终交互

- **永远有一个块展开**：指针不在条上（或落在间隙）时块 0 展开。
- **收起瞬时（0 ms）、展开 100 ms 线性**。收起瞬时是唯一能让"只有右边界动"成立的做法：
  块 i 的左边界 = 前面块当前宽度之和，收起只要还有动画，后面所有块就被一路带着左移，
  看起来就是"先向左再向右"。
- **底色始终全亮度**，收起态只靠 35% 白的单字区分；展开态文字 100% 白。
- **五套色相**：绿（主）/ 蓝（钩）/ 紫（学）/ 橙（名）/ 青（志），每套四档状态，
  共 20 个互不重复的色值。**未启用用去饱和而不是提亮**——提亮会让它比"正常"的暗态还亮。
- **文字左对齐**：单字居中 + 长文左对齐的交叉淡入，会让人看到"文字从中间向两头展开"。
- `SETTINGS_STATUS_SLACK 6`：目标宽度 = 测宽 + 2×PAD + 6，末字不再被裁。

### 20.2 这一轮抓到的两个真 bug

1. **收敛帧不重绘**：`if (progress >= 1.0f) { width = to; }` 没置 `moving`，最后一帧
   改了宽度却不画，屏幕停在上一个约 96% 的帧，末字被切；鼠标再动一下触发重绘才完整。
   **修法**：收敛帧判断宽度是否真的变了，变了就多画一帧。
2. **`SS_OWNERDRAW` 的静态控件默认对鼠标透明**（`HTTRANSPARENT`），不加 `SS_NOTIFY`
   永远收不到 `WM_MOUSEMOVE`（§19.5）。

### 20.3 全链路审计后的修复

**自学习**
- **采样加 `blocked`**：只采确实被拦下的按下。原来"固定窗口、不看判定"会把一次 55 ms 的
  正常双击（阈值 50 放行）采样进去，建议推到 56，采纳后开始吞点击——这比不学更糟。
- **采用时按当前阈值重新做 ±50% 限幅**：缓存的建议不会因用户手动改阈值而失效。
- **采用只作用于菜单显示的 L/R/M**，不再悄悄改 X1/X2，也不会"只有侧键有建议时入口是灰的"。
- **建议等于当前阈值时返回 0**：否则点了什么都不变，样本却清零，还提示"已采用"。
- **`signal_ring_note_interval` 先写桶再写计数**，消除"样本够 33 但没有建议"的窗口。
- **`learning_service_stop` 超时不再关句柄**（工作线程会 use-after-free），并让后续
  `start` 拒绝而不是起第二个线程。
- **采用后先清 ring 再清建议缓存**，避免建议在 100 ms 内复活。

**黑白名单**
- **迁移结果立即落盘**。原来只改内存、标记已写死，升级用户重启后规则和模式双双丢失。
- 迁移时 `trim`；带路径的旧条目按完整路径存（`*\C:\...` 永远匹配不上）。
- 读注册表改 `KEY_READ`，迁移单开写权限：只读键不再导致整表丢失。
- 白名单为空时切到白名单模式先弹确认（等于关闭全部过滤）。
- 名单满 16 个时"添加程序"置灰。
- 子菜单单选勾按**本名单是否为当前模式**，不再按"只要不是全部程序"。
- 添加成功提示带程序名；添加后立即落盘（与删除一致）。

### 20.4 仍然没修（已在代码里确认的已知限制）

1. **自学习样本不持久化**：每会话清零，偶发抽风的鼠标可能永远攒不到 32；菜单也不显示
   目标值，用户不知道还差多少。
2. **建议生成后没有主动提示**，只在二级菜单里能看到。
3. ~~名单解析失败时沿用上一个程序的判定（该拦的可能被放行）~~ —— **已在 §21.2 修复**。
4. **一键项在"规则已存在但名单未启用"时不切模式**，点了像没反应。
5. **名单项只显示文件名**，同名不同路径分不出来。
6. `context_filter` 的 `suppress` 系列命名与实际语义（放行）相反；改动风险大，保持现状。
7. `GetTickCount64` 的 15.6 ms 量化让建议值精度只有档位级。

### 20.5 新增契约

24. **宽度动画用固定时长**（展开 100 ms / 收起 0 ms），不用"每帧按比例逼近"；收敛帧必须重绘。
25. **块位置由前面块的当前宽度决定时，收起必须瞬时**，否则"只向右展开"不成立。
26. **学习采样必须以"被拦下"为证据**：放行的按下不构成需要调整阈值的事实。
27. **建议值在采用出口必须按当前阈值重新限幅**，不能信任缓存的钳制结果。

## 21. 底部状态栏 + 名单 fail-closed（2.4.2）

### 21.1 状态栏

用户提出「给窗口底部加一条默认状态栏，以后提示、状态都往这里放」。采纳，理由不是
"多一条装饰"，而是它补了一个真实的信息空白：**没有任何地方告诉用户当前前台程序是被拦
还是被放**。顶部 5 色块只说明"名单模块在不在工作"，不说判定结果。

- **原生 `msctls_statusbar32`**，两格：`[当前程序判定 120 DLU] [消息 弹性]`
- 第一格 120 DLU（约 180 px），**刻意小于窗口四分之一**。这条栏以后要承载别的东西，
  第一格吃满就没地方放了
- 对话框 `299 → 311 DLU`，**现有控件一个坐标没动**。挤压布局要重排状态条、图表、
  两个窗格、四个按钮，那才是真正会做坏的地方
- 抽成 `src/ui/status_bar.c/h` 而不是写在 `settings_window.c`：用户已明确说后面还要
  加窗体。从第二个窗体开始，每个省 60 行重复代码，两窗的分格、字体、位置也不会各自漂移

**第一格的四条文案**（`AppSnapshot` 新增 `context_verdict` + `context_name`）：

| 条件 | 文案 |
|---|---|
| `slot->ours` | `本程序窗口` |
| `slot->pid == 0` | `等待前台程序` |
| `slot->suppressed` | `已排除：xxx.exe` |
| 其余 | `已拦截：xxx.exe` |

**读快照不加锁**：`context_filter_publish` 是双缓冲——写非当前槽再翻转索引，
读 `slots[current]` 看不到半更新的槽。

**没有新增 `InitCommonControlsEx`**：`main.c` 早已用 `ICC_WIN95_CLASSES` 初始化，
它包含 `ICC_BAR_CLASSES`。这一点曾经差点被误判成"必须新增"。

### 21.2 名单 fail-closed（§20.4 第 3 条）

`context_service.c` 的解析失败分支原来是 `last_pid = 0; continue;`，注释写着"保留上一次
发布的槽"。问题在于那个槽属于**上一个程序**：从黑名单命中（放行）的 A 切到认不出的 B，
B 继续被放行；反之继续被拦。两个方向都错，且完全静默。

改成发布 `pid = 0` + 不豁免：

```c
context_filter_publish(service->filter, 0, false, false, L"");
```

`publish` 内部 `apply = suppressed && !ours && pid != 0`，所以 `pid = 0` 必然落到"拦截"。
`observed` 不动，顶部「名单」块因此显示**待数据**而不是「正常」——不可见的状态反而
变得可见。

**代价**：受保护进程（游戏反作弊等）即使被用户手动排除也会被拦。影响面小，方向与项目
其他部分一致：宁可多拦，不可漏拦。

**这一支没有自动化覆盖**：`context_thread` 是轮询线程，单测够不到；冒烟也造不出
"前台可解析 → 失败"的场景（需要 PPL 进程或提权）。只能靠代码审查，不要声称它被测试
覆盖了。

### 21.3 新增契约

28. **每个带状态的窗口底部用 `status_bar_attach`，不要在窗口里手写初始化**：
    `InitCommonControlsEx`、贴底定位、字体继承三件事各有各的静默失败方式。
29. **状态栏第一格显示"正在发生什么"，不是"配置成什么"**：用户要的是拦截结果，
    不是模式名称。
30. **原生状态栏的分格宽度要减掉 `SB_GETBORDERS`**，否则最后一格跑出右边界被裁剪。
31. **对话框加控件优先"加高窗口"，不要"挤压现有布局"**：改一个数字 vs 重排整个
    模板，后者是回归的主要来源。

## 22. 状态栏消息通道（2.4.2）

### 22.1 为什么放应用层

`status_notice`（`src/core/status_notice.{c,h}`）是一个只有一条消息的槽：文字 +
过期时刻 + 重复抑制。放在 `AppState` 里，不在窗口里。

理由：**产生消息的动作在 `main.c`，那时窗口很可能没开**（托盘运行、用户没点开体检
窗口）。消息存窗口里，窗口关闭期间发生的事就丢了，用户再打开看到的是"什么都没发生"。

窗口侧只做一件事：每 400 ms 刷新时读一次快照。**过期判断也在读的时候做**，所以窗口
不需要第二个定时器。

### 22.2 只播报两类事件

评估过"保存成功""名单添加成功""学习建议生成"，都**没有采纳**：

| 候选 | 为什么不做 |
|---|---|
| 配置已保存 | 滑块每拖一次就保存一次，状态栏会变成滚动字幕 |
| 名单添加成功 | 菜单项点完就消失，用户已经在同一屏看到结果 |
| 学习建议生成 | 需要先有"生成即提示"的产品决策，不在这一轮 |

留下的是**用户否则完全不知道**的两件事：

| 事件 | 文案 | TTL |
|---|---|---|
| 钩子被系统丢弃后自动恢复 | `已自动恢复鼠标钩子` | 8 s |
| 配置写盘失败 | `设置保存失败，重启后会丢失` | 10 s |

**第二件比第一件更该说**：只读注册表下每次修改都会静默丢失，气泡只报一次，
状态栏每次都报。

### 22.3 重复抑制

同一句话在 30 秒内不刷新 TTL。看门狗在提权窗口里可能每 30 秒恢复一次钩子，没有抑制
的话状态栏会永久显示同一行，比不显示更糟。

**抑制按文字判定，所以带变量的文案会绕过它**。钩子恢复的文案因此**不带次数**
（`已自动恢复鼠标钩子`，不是 `第 3 次恢复`）——次数在托盘提示和日志里。

### 22.4 验证

新增 `test_status_notice`（22 条断言）：空槽、正常显示、空文字撤回、过期自动清除、
重复抑制不改 `shown_tick`、不同文字不被抑制、cleanup 后失效。

真机：临时 post 一条 `ZZTEMP 临时消息验证`，`SB_GETTEXTLENGTHW` 读到 `len0=5`
（`本程序窗口`）、`len1=13`（`ZZTEMP 临时消息验证`），`PrintWindow` 截图确认两格
都在。`IsHungAppWindow=False`、`SendMessageTimeout(WM_NULL)` 1 ms 返回，UI 线程
没有被锁死。**验证完已删除临时 post。**

四配置 Rebuild（含 `/analyze`）0 error 0 warning；单测 x64 / x86 **3382 / 0**；
`audit_printf.py` PROBLEMS: none；`e2e` / `diagnose` / `stuck_key` 各 0 failure。

### 22.5 新增契约

32. **状态栏消息存应用层，不存窗口**：动作发生时窗口可能没开，存窗口等于丢消息。
33. **过期在读取时判定，不起第二个定时器**：读的那一方本来就在周期性刷新。
34. **重复抑制按文字判定，所以带变量的文案会绕过它**；需要被抑制的文案不要带次数。

## 23. 学习建议主动提示（2.4.2）

### 23.1 痛点

`learning_advice_from_ring` 每轮全量重算，`suggested_ms[i] == 0` 表示证据不足。建议
**只通过托盘右键菜单被动展示**，`learning_service` 的 worker 线程没有任何回调。

结果：一个从不打开托盘菜单的用户，即使样本早已足够，也**永远不知道**有东西可采纳。
这是 §20.4 的第 2 条。

### 23.2 方案：复用刚刚做好的消息通道，不新增 UI

没有选择「气泡」或「菜单项高亮」，因为：

- 气泡已经被 §UI 约定限制为"两行、不额外加内容"，且系统勿扰会让它静默
- 菜单每次右键重建，加标记也要用户先右键，痛点没变

采用的是**状态栏消息**：

```
体检窗口刷新（400 ms）
  → learning_service_snapshot
  → learning_advice_visible_count
  → 数量与上次数不同 → status_notice_post("有 N 项阈值建议可在托盘菜单采纳", 10 s)
```

**只在数量变化时 post**，不是每次刷新。采纳后数量回到 0，把记录清零，所以同一个数字
再出现时会重新提示。

### 23.3 只数三个键

`learning_advice_visible_count` 只统计 `LEFT / RIGHT / MIDDLE`，与菜单渲染、采用时的
`shown[]` 是同一组。

X1/X2 的采样和建议都是真实的，但**菜单不渲染、采用时也跳过**（§20.3）。数进去会让
提示说「3 项」，用户打开菜单只看到 2 项，然后去找第三个——一个不存在的东西。

### 23.4 已知限制

**这个提示同样只在体检窗口打开时产生**。窗口关着时建议生成，用户不会立刻被通知；
等他下次打开窗口，`advice_notice_count` 仍是 0 而实际数量非 0，于是补一次提示。

这是有意的：建议不是"必须现在处理"的事件，样本会一直累积到被采纳。**即时弹窗会打扰
正在工作的用户**，而打开窗口时告知已经足够。

代价要说清楚：**如果用户从不打开体检窗口，也从不右键托盘菜单，他仍然不会知道。**

### 23.5 验证

新增 11 条断言（单测 3382 → **3393**）：全 0 不计、单键计 1、双键计 2、**仅侧键计 0**、
NULL 计 0。

真机临时 post `有 2 项阈值建议可在托盘菜单采纳`：`SB_GETTEXTLENGTHW` 得 `p1len=17`
（与文案长度一致），`PrintWindow` 截图确认第二格完整显示，没有被截断。验证完已删除。

四配置 Rebuild（含 `/analyze`）0 error 0 warning；单测 x64 / x86 **3393 / 0**；
`audit_printf.py` PROBLEMS: none；`e2e` / `diagnose` / `stuck_key` 各 0 failure。

### 23.6 新增契约

35. **"有几项可操作"必须与"菜单实际显示几项"同一口径**：把菜单不渲染的项数进去，
    等于让用户去找不存在的东西。
36. **提示只在数量变化时发**，不在每次刷新时发；数量归零要重置记录，否则同一个数字
    不会再提示。

## 24. 名单项显示可区分的路径（2.4.2）

### 24.1 问题

`context_menu.c` 用 `context_file_name_from_path` 渲染名单项，只显示 `game.exe`。
两条规则分别指向 `D:\Games\game.exe` 和 `E:\Backup\game.exe` 时，菜单里完全一样，
**点哪一条会删掉哪一条只能靠猜**。这是 §20.4 的第 5 条。

### 24.2 关键判断：必须中间省略，不能末尾省略

直接换成完整路径看起来对，实际不行：**Windows 菜单本来就从右边裁剪**，而文件名正好
在右边——一条超长路径被它裁完，剩下的正是唯一能区分的部分被去掉。

所以 `context_shorten_path` 做的是**中间省略**：

```
D:\Games\game.exe                                    （66 字符以内，原样）
C:\Users\someo…Programs\Product\bin\app.exe          （超过 64，保留头 26 + 尾 28）
```

- 阈值 `CONTEXT_MENU_PATH_CHARS 64`
- 头 26 字符保留盘符和一级目录，尾 28 字符保留文件名和邻近目录
- `StringCchPrintfW` 失败（调用方缓冲区太小）时退回文件名，不留空菜单项

### 24.3 只改显示，不改删除

菜单项 ID 仍是 `item_base + i`，删除按**索引**而不是按文本回查路径。所以：
- 显示变化不影响任何删除逻辑
- 两条同名规则各自对应自己的索引

### 24.4 验证

9 条断言（单测 3393 → **3402**）：短路径原样、长路径变短且含 `…`、**文件名必须仍在
末尾**、**同名的两个不同盘符渲染结果必须不同**、NULL / 空串不留垃圾。

这个改动**没有做真机菜单截图**：构造两条同名规则需要改用户配置，而格式化逻辑本身
已被单测覆盖，调用点只是换了一个函数。若要补，用 `e2e.ps1` 的配置还原机制构造即可。

四配置 Rebuild（含 `/analyze`）0 error 0 warning；单测 x64 / x86 **3402 / 0**；
`audit_printf.py` PROBLEMS: none；`e2e` / `diagnose` / `stuck_key` 各 0 failure。

### 24.5 新增契约

37. **菜单里显示"可区分标识"时只能中间省略**：末尾省略会删掉文件名，正是需要保留的
    那一段。
38. **显示层改动不许改变菜单项 ID 的语义**：ID 按索引，删除不按文本回查。
