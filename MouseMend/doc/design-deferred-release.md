# 设计方案：把延迟松手的注入移出钩子回调

状态：**v1 已被评审否决，v2 见 §9；已实施** —— 代码在 `debouncer.c` 的延迟释放
路径与 `release_delay_ms` 设置，实施清单见 `impl-deferred-release.md`
日期：2026-11-25
关联：`debouncer.c` / `main.c`

> **2026-11-26 更新（2.3.0）：本文的「重放按下」部分已废除，实现已删除。**
> 实机日志证明：扣住松手期间到来的那个「按下」，对磨损的开关来说就是抖动本身；
> 重放 `UP → DOWN` 等于替用户重新按住按钮，一旦这个抖动没有对应的松开，按钮就
> 永久按下（窗口跟手，点一下才解）。现在改为：按下直接拦下、扣留状态保留、
> 定时器只补发一个 UP，并且**扣留默认关闭**（`Release Delay = 0`）。
> 「把注入移出钩子、交给定时器」这个结论仍然有效，本文其余部分保持原样以便对照。

> **读之前先看 §9。** §1-§8 是 v1，保留原文以便对照；其中 §3 的调用点清单、§4.3 的线程载体、§4.4 的取消规则、§4.5 的失败降级**都有错**，已于 §9 修订。

## 1. 问题

2026-11-25 两台机器上各挂死一次，用户机上抓到的 minidump 给出了符号级证据：

```
win32u!NtUserSendInput            ← 线程永久停在这里
MouseMend+0x617F   release_deferred_button    → debouncer.c:126 SendInput
MouseMend+0x6226   debounce_process_event_ex  → debouncer.c:209 flush-on-press
MouseMend+0x111E   OnMouseHookCallback        → main.c:222
MouseMend+0x744C   LowLevelMouseProc          → mouse_hook.c:47 manager->callback
```

低级鼠标钩子的回调跑在**安装钩子的那个线程**上（UI 线程）。`SendInput` 注入的事件还要再过一遍钩子链，而链头正是这个线程自己 —— **自等待，永不返回**。

后果链：
- 输入链被堵 → 全系统鼠标卡滞，直到 `LowLevelHooksTimeout` 到期，Windows 静默摘掉钩子
- 摘钩子只解救了系统，**救不了已经陷在 `win32k` 里的线程** → 消息循环死掉，窗口再也打不开
- 线程在内核调用里出不来 → `TerminateProcess` 只能打标记 → 进程变成退不掉的僵尸，**只能重启**

## 2. 目标 / 非目标

**目标**
1. 钩子回调内**不再出现任何 `SendInput`**。
2. 智能拖拽的行为对用户**保持原样**：拖动后松手被推迟，随后快速按下仍然算一次新的点击。
3. 任何失败路径都不能导致按钮在系统里卡在按下状态。

**非目标**
- 不改去抖判据本身（阈值、拖拽距离、推迟时长都不动）
- 不改其余五个注入调用点（见 §3，它们本来就安全）
- 不引入驱动、不提权

## 3. 现状：六个注入调用点

全部注入都汇聚到 `release_deferred_button()`（`debouncer.c:64`），它内部唯一危险的动作是 `debouncer.c:126` 的 `SendInput`。

| 调用点 | 所在线程 | 是否在钩子内 | 处置 |
| :--- | :--- | :--- | :--- |
| `debounce_process_event_ex`（`debouncer.c:209`） | UI（钩子线程） | **是** | **改异步** |
| `debounce_check_deferred_releases`（`debouncer.c:750`，WM_TIMER `main.c:1346`） | UI | 否 | 不动 |
| `debounce_flush_deferred_releases`（`debouncer.c:760`） | UI | 否 | 不动 |
| `debounce_set_monitored`（`debouncer.c:516`） | UI（菜单） | 否 | 不动 |
| `debounce_set_all_monitored`（`debouncer.c:543`） | UI（菜单） | 否 | 不动 |
| `debounce_cleanup`（`debouncer.c:52`） | UI（退出） | 否 | 不动 |

**结论：只需要改一个调用点。** 其余五个都在钩子返回之后执行，不构成自等待。

## 4. 方案 A：钩子只改状态，注入交给独立线程

### 4.1 两个新动作

把现在那一行的"清状态 + 注入"拆成两半：

- **`take_deferred_release(manager, button, &up_flags, &up_data)`** —— 只改状态（清 `isDeferringRelease`、更新 `previousTime`），**返回要注入的 UP 参数**，不调用 `SendInput`。给钩子用。
- **`release_deferred_button(manager, button, force)`** —— 保持不变，给其余五个安全调用点用。

两个函数共用同一段"按钮 → MOUSEEVENTF"的映射，抽成 `button_up_flags()`，避免两份会漂移的表。

### 4.2 钩子路径的新时序

现在（危险）：

```
按下到达 → 注入 UP（同步） → 放行按下      系统看到：UP, DOWN
```

改后（安全）：

```
按下到达 → take_deferred_release（只改状态）
         → 拦下这次按下（return 1）
         → 提交一条注入请求：[UP, DOWN]
注入线程 → SendInput(UP) → SendInput(DOWN)   系统看到：UP, DOWN（对用户等价）
```

顺序靠**一条请求内保序**保证，不依赖两次投递的先后。

**为什么必须连按下一起拦下重放**：异步化之后，如果先放行按下、再注入 UP，系统看到的顺序会变成 DOWN（此时系统认为键已按下，被忽略）→ UP，净效果是**这次点击丢了**。所以只能拦下再重放。

### 4.3 注入线程（`src/core/injector.c`）

```c
typedef struct { DWORD flags; DWORD mouse_data; } InjectStep;

typedef struct
{
    InjectStep steps[2];      // 一条请求最多两步，保证 UP 在 DOWN 之前
    int step_count;
    int button;               // 用于取消判定
    uint64_t press_time;      // 提交时的按下时间戳
} InjectRequest;
```

- 线程在 `InitializeApp` 里创建，早于钩子安装，**保证钩子路径上不会因为创建失败而退化**
- 有界队列（16 条）+ 自动重置事件唤醒；队列满就丢弃并计数（**绝不阻塞钩子**）
- 单条请求内按序注入，天然保证 UP → DOWN
- 退出时 `injector_stop()`：置停止标志、唤醒、`WaitForSingleObject` 1 秒超时，超时就放弃（进程要退，不能为了它卡住）

**注入 DOWN 时不要带 `MOUSEEVENTF_MOVE`。** 只发按键标志，按当前光标位置按下。理由是避免绝对坐标归一化在多显示器 / 非整数 DPI 下算错导致光标跳位。重放与原始按下相隔不到 1 毫秒，位置差异可以忽略。

### 4.4 取消规则（防止按钮卡在按下）

危险场景：请求已提交，但用户**在注入线程执行前就松手了**。此时系统状态是 UP，注入线程再把 DOWN 发出去 → 系统认为按下、实际已松手 → **按钮卡住**。

两层防护：

1. **钩子侧（主）**：每个按钮加 `pending_replay` 状态。真实 UP 到达且时间戳晚于 `press_time` 时，清掉 `pending_replay`。注入线程取请求时若发现已被清掉，就**连 UP 一起跳过**（UP 此时也无意义）。
2. **注入线程侧**：取到请求后、注入之前再核一次状态。

两层之间仍有微秒级窗口，接受这个残留风险，并在文档里写明：最坏情况下系统认为按键处于按下状态，用户的**下一次**物理点击会自愈（按下被忽略、松开时释放）。

### 4.5 失败路径

| 情况 | 处置 |
| :--- | :--- |
| `injector_submit` 失败（队列满 / 线程已停） | **不拦按下**，照常放行；UP 交给定时器补发。代价是这一次点击丢失，但不会卡键 |
| 注入线程创建失败 | 启动时报错并**不安装钩子**（宁可防护不可用，也不能埋一个会卡死的路径） |
| 注入线程内部异常 | 丢弃请求并计数；不影响钩子 |

### 4.6 对决策与统计的影响

- `DebounceDecision` 增加一个 `bool replay`，函数入口置 false
- 命中 flush-on-press 时：`reason = DEBOUNCE_REASON_PASS_FLUSHED`（**沿用现有文案"通过+补发"**，对用户语义不变），`replay = true`，`blocked` **仍为 false**
- `OnMouseHookCallback` 里：`if (decision.replay) return 1;` 放在 `if (blocked)` **之前**，因此
  - 不计入 `blocks`（它不是被拦下的误触）
  - 不写拦截日志、不弹气泡（同上）
  - 自检证据（`evidence[]`）不更新（同上）

## 5. 关键不变量

1. **钩子回调内不得出现 `SendInput` / 文件 IO / 跨进程调用。** 新增代码必须遵守，评审时逐行核对。
2. `isDeferringRelease == false` 当且仅当系统已经（或即将）收到这次 UP。任何清标志的路径都必须伴随一次投递，**不允许只清不发**。
3. 一条注入请求内 UP 必在 DOWN 之前。
4. 提交失败时必须退回"放行按下 + 定时器补发"，不得吞掉事件。

> 不变量 2 是本次改动必须守住的底线。`debouncer.c:286` 那个分支今天正好违反它（只把 `isDeferringRelease` 置 false 而不发 UP），只是因为 `debouncer.c:209` 先 flush 过才没暴露。**这就是"只删那行 flush"会导致按钮永久按下的原因。**

## 6. 自审：发现的问题与结论

| # | 问题 | 结论 |
| :-- | :--- | :--- |
| 1 | 只删 `debouncer.c:209` 的 flush 会怎样 | **不可行**。`debouncer.c:286` 分支会把标志清掉却不发 UP → 按钮在系统里永久按下。必须异步补发 |
| 2 | 可否用 `PostMessage` 给自家窗口，在消息里注入 | 可行但更脆：注入会依赖 UI 线程空闲（例如刷新诊断面板时会延迟）。选中独立线程 |
| 3 | 可否在钩子里同步等注入线程完成 | **绝对不行**。同步等待 = 钩子不返回 = 输入链照样堵死，而且是等待一个依赖输入的线程，仍是自等待 |
| 4 | 重放导致一次点击变成注入事件 | 现有设计**本来就在注入 UP**，不是新增类别；自家钩子对 injected 事件直接忽略（`debouncer.c:235`），不会自激 |
| 5 | 重放位置是否需要绝对坐标 | 不需要，且不该用。只发按键标志，避免 DPI / 多屏归一化误差 |
| 6 | 定时器路径是否也要异步 | 不需要。WM_TIMER 在消息循环里执行，不在钩子内 |
| 7 | 注入线程会不会自己被堵 | 不会。它调用 `SendInput` 时钩子线程已返回，条件不成立。极端情况下最多是延迟 |
| 8 | 新增线程对"单线程可调试"的影响 | 有。调试与崩溃报告里会多一个线程；`support_bundle` 的线程快照需要能看出它 |
| 9 | 性能 | 每条请求一次事件唤醒 + 两次 `SendInput`，仅在"松手被推迟时又按下"发生，量级可忽略 |

由两路独立评审（架构视角 / 代码正确性视角）对 v1 逐行核对。**结论：方向成立，但 v1 有 4 处硬伤，均已在 v2 修订。**

## 9.1 被推翻的论断（我已逐条复核）

| # | v1 的说法 | 事实 | 严重度 |
| :-- | :--- | :--- | :--- |
| **R1** | §3「只有 1 个注入点在钩子内」 | **错。有两个。** `main.c:207-210` 的 `EnsureDeferredReleaseTimer` 在 `SetTimer` 失败时会**同步**调 `debounce_check_deferred_releases` + `debounce_flush_deferred_releases`，而它由 `main.c:261` 在**钩子内**调用。按 v1 实施，事故原样复现 | **致命** |
| **R2** | §3「共 6 个注入调用点」 | **错，是 8 个**（漏了 `debouncer.c:456` `debounce_set_hybrid_heuristic`、`debouncer.c:698` `debounce_reset_statistics`） | 中 |
| **R3** | §4.4「真实 UP 到达 → 清 `pending_replay` → 跳过 UP 和 DOWN」 | **判据方向对，但不够**：若注入线程已取走请求（`IN_FLIGHT`），那个 UP 已经放行给系统，此时再补一个 DOWN 就是**凭空按下** → 按钮卡在按下态，且**不会自愈**（下次按下会被系统当作"已按下"忽略） | **致命** |

| R5 | §5「不变量 2 当且仅当」 | 反向不成立；应改为"任何把 `isDeferringRelease` 从 true 改成 false 的路径，都必须有一个对应的 UP 投递计划" | 中 |
| R6 | §4.3「重放 DOWN 不带 MOVE，位置差异可忽略」 | 位置差异**不是 1 ms 的问题**：`downPoint` 记的是按下点，注入点在当前光标处，两者差值会被下次 `debouncer.c:379-380` 的拖拽判据当成位移，可能把一次普通点击误判为拖拽 | 中 |
| R7 | §4.6「`replay = true` 时放行按下」 | 若 `decision == NULL`（`debouncer.c:1016` 的测试就这么调）则写入会崩；且 `blocked=false` + UI `return 1` 会让"判定只有一份"这条铁律出现分裂 | 中 |
| R8 | §4.5「注入线程创建失败 → 不安装钩子」 | `InitializeApp` 在 `WM_CREATE` 里（`main.c:1338`），此时窗口**已创建**，第二个实例的 `FindWindowW` 会找到半死实例并给僵尸窗口发消息 | 中 |

复核方式：`main.c:196-211` 与 `Select-String release_deferred_button` 全量调用点，逐行核对，**R1 与 R2 确认成立**。

## 9.2 v2：换载体——不用线程，复用现有的 15 ms 定时器

v1 引入注入线程后，评审在它周围找出了**一整类**问题：退出时 `WaitForSingleObject` 超时后临界区已被销毁而线程仍在跑（未定义行为）、队列满导致跨请求乱序（A 的 DOWN 已发、B 的 UP 被丢 → 卡键）、`ShutdownApp` 顺序与拔钩子的先后。这些问题**全部是"多一个线程"带来的**，而不是问题本身需要的。

**v2 不引入任何线程。** 回到项目已有的模式："钩子只置标志，定时器消费"（`main.c:281-290` 的注释就是这么写的）。

- 注入仍然发生在 `TIMER_DEFERRED_RELEASE`（15 ms，`main.c:1343`）的处理里 —— **不在钩子回调内**，自等待条件不成立
- 这条路径**已经被现有代码验证了几个月**（推迟松手平时的 UP 就是从它的 `debounce_check_deferred_releases` 发出的）
- 代价：额外最多 15 ms 延迟。人眼对 15 ms 无感；而且只在"推迟期间又按下"这种罕见情形出现

**因此 v1 的 §4.3 整节作废**，`src/core/injector.c` 不需要存在。

## 9.3 v2：让"推迟"以定时器可用为前提（消灭 R1）

R1 的兜底之所以存在，是因为"吞掉 UP"的决定发生在 `debounce_process_event_ex` 内部，等 `EnsureDeferredReleaseTimer` 发现 `SetTimer` 失败时为时已晚。

v2 把顺序倒过来：

1. **每次物理按下时**（钩子内，`is_down && !is_injected`）：若智能拖拽启用且定时器未武装 → `SetTimer` 一次。**失败就置 `smart_drag_unavailable = true`**。
2. **决定推迟时**增加前置条件：`smart_drag_unavailable == false`。不可用就**不推迟**，UP 正常放行（用户感觉是"这一次没保护到"，而不是卡键）。
3. **`main.c:207-210` 的兜底分支整段删除** —— 它存在的理由消失了，而它正是第二条钩内 `SendInput`。

这样"钩子回调内不出现 `SendInput`"才真正成立，而且是结构上成立，不是靠运气。

## 9.4 v2：握手机制（修 R3）

每个按键增加两个状态：`replay_state ∈ {NONE, QUEUED, IN_FLIGHT}`、`release_during_replay`。

| 时机 | 动作 |
| :--- | :--- |
| 钩子：推迟中收到按下 | 置状态（清 `isDeferringRelease`）、`replay_state = QUEUED`、**拦下这次按下**。不调用注入 |
| 钩子：收到真实 UP，且 `QUEUED` | 注入还没开始 → 取消整个重放，**UP 放行**（此时系统仍认为按下，放行后状态即一致） |
| 钩子：收到真实 UP，且 `IN_FLIGHT` | 注入已经在发 → **吞掉这个 UP**，置 `release_during_replay = true` |
| 定时器：处理重放 | 临界区内把 `QUEUED → IN_FLIGHT`；注入 UP；注入 DOWN；临界区内检查 `release_during_replay`，为真则**再补一个 UP**，然后置 `NONE`、清标志 |

关键：**"置 NONE + 读 `release_during_replay`"必须在同一个临界区里完成**。这样任何在它之后到达的 UP 都会看到 `NONE` 并正常放行，事件不会丢。

**残留风险（必须写进文档，不许声称"自愈"）**：若注入本身卡住，`IN_FLIGHT` 会一直挂着，期间的 UP 被吞掉 → 按钮卡在按下。因此加超时：`IN_FLIGHT` 超过 200 ms 就由钩子强制回落到 `NONE` 并放行后续事件，同时记一次诊断计数。

## 9.5 v2：其余修订

- **R4**：`replay_state = QUEUED` 是一个纯内存标志，**不会失败**，所以 v1 的"提交失败"整条路径消失。唯一的前置失败（定时器不可用）已在 §9.3 前移到"决定是否推迟"的时刻。
- **R6**：重放 DOWN 改用 `MOUSEEVENTF_MOVE | MOUSEEVENTF_ABSOLUTE`，坐标取被拦下那次按下的 `event->x/y`，用 `SM_XVIRTUALSCREEN / SM_CXVIRTUALSCREEN` 归一化（`MSLLHOOKSTRUCT.pt` 本来就是屏幕坐标，不需要 DPI 换算）。这样系统记录的按下点与 `downPoint` 一致。
- **R7**：`replay` 不进 `DebounceDecision`。改为新增 `debounce_process_event_verdict()` 返回三态 `{PASS, BLOCK, REPLAY}`，钩子用它；`debounce_process_event_ex` 保留为薄包装（`REPLAY` 同样返回"拦下"），现有测试不受影响。
- **R5**：不变量 2 改写为"任何把 `isDeferringRelease` 置 false 的路径，都必须有一个对应的 UP 投递计划"。
- **`previousTime` 单点写入**：`take` 不写 `previousTime`（v1 §4.3 要写，是多余的——`debouncer.c:324` 随后会用事件时间戳覆盖），删除 `debouncer.c:91` 那次 `GetTickCount64()` 写入，避免两处打架。
- **`button_up_flags()`**：返回 `bool`，内部保留 `if (!flags) return false`（滚轮不走 UP），调用方必须检查。
- **`data->blocks` 不变**：重放不是"拦下误触"，不得 `blocks++`，否则用户看到的拦截数会虚高。

## 9.7 实测：模态循环期间定时器仍然工作（2026-11-25）

v2 的载体是 15 ms 定时器，但它必须在**托盘菜单打开时**仍然派发，否则重放会被推迟到菜单关闭、按钮在那之前一直是按下状态。这一点不能靠推理，写了个独立的最小程序实测（`TrackPopupMenuEx` + `MessageBoxW` 两类模态循环，各约 1.5 秒，同时记录定时器跳数和 `SendInput` 调用结果）：

| 阶段 | 经过 | 定时器跳数 | 理论值 | `SendInput` 成功 |
| :--- | ---: | ---: | ---: | ---: |
| `TrackPopupMenu`（托盘菜单的情况） | 1500 ms | **95** | 约 96 | **95 / 95** |
| `MessageBox`（另一种模态循环） | 1578 ms | **95** | 约 101 | **95 / 95** |

**结论：模态循环期间 `WM_TIMER` 照常派发，且从定时器处理函数里调用 `SendInput` 每次都成功。** v2 用定时器做注入载体成立，§9.6 第 2 条的风险排除。

## 9.8 关于"上驱动 / 上服务 / 提权"的评估（2026-11-25，倾向不做）

用户提出"只要能完美解决，不介意突破不做驱动/服务的初衷，但不会买签名"。

**结论：这三条对本问题都没有收益，其中两条在现代 Windows 上不可分发。**

| 方案 | 能不能解决本 bug | 实际代价 |
| :--- | :--- | :--- |
| **内核过滤驱动**（如 Interception，直接在驱动层截留 UP） | 能**绕过** `SendInput`，但**绕不过**"注入必须在钩子外"这条约束——它只是换了一种注入方式 | **x64 下必须微软签名**：自签名只能开测试模式（桌面水印、不能分发、用户要手动改 bcdedit）。这个项目**发不出去** |
| **系统服务** | 不能。服务在 session 0，`WH_MOUSE_LL` 是**每桌面/每会话**的，看不到交互会话的输入 | 要跨会话注入，复杂度暴涨，收益为零 |
| **提权运行（管理员）** | 不能。死锁是**线程拓扑**问题（RIT 等钩子回调返回，而回调就在调用 `SendInput` 的同一个线程上），与完整性级别无关 | 每次启动 UAC、自启动要改用计划任务、**被杀难度上升**（上一轮"权限不足"很可能就是这个原因）。唯一真实收益是 UIPI：前台程序提权时我们的注入会被静默丢弃——但那是另一个问题，应该**检测并提示**，不是靠提权 |

**判断依据**：本设计里注入是**躲不掉**的（每次拖动松手都要把吞掉的 UP 补发回去），所以问题从来不是"权限不够"，而是"从哪个线程发"。把注入搬到定时器里，用户态就能彻底解决。

**顺带记录三条不需要任何权限、但确实能让它更稳的事**（尚未实施）：
1. **挂起看门狗**：独立线程监测 UI 线程心跳，超过阈值就用 `MiniDumpWriteDump` 抓一份挂起转储。这次事故是**手工**抓的，产品自己抓不到挂起（只捕获崩溃）。
2. **结构守门**：所有注入收敛到 `inject_mouse()`，在钩子回调里调用就断言/拒绝（Debug 断言 + Release 计数），防止未来再往钩子里塞注入。
3. **UIPI 失败可见化**：`SendInput` 返回 0 时记录并提示，而不是静默丢掉一次松手。

# 10. 第一原则：能放弃，不等待

由用户提出："别让他等，或者告诉他已经不用等了；加个保底，以后遇到类似问题就丢弃掉，不用等。"

**这个原则是对的，而且是本设计最重要的一条**，但要先说清它的边界。

## 10.1 它救不了已经卡住的线程

进程一旦有线程陷在 `win32k` 的系统调用里，**用户态没有任何办法让它出来**：

| 手段 | 对"卡在内核等待里的线程"的效果 |
| :--- | :--- |
| `TerminateProcess` / `taskkill /F` | 只打终止标记，线程返回用户态时才真正退出 → **不退** |
| `TerminateThread` | 同上，且更危险 |
| `SuspendThread` + `SetThreadContext` 改 RIP | 上下文要等线程回到用户态才生效 → **无效** |
| `CancelSynchronousIo` | 只能取消同步 I/O，`NtUserSendInput` 不是 I/O → 基本无效 |
| `NtAlertThread` | APC 只能打断**可警醒**的等待 → 大概率无效 |
| 提权 / 驱动 | 与线程拓扑无关（见 §9.8） |

**结论：这是"设计期"的原则，不是"事故期"的解药。** 它必须写在所有可能阻塞的调用之前，没法事后补救。

## 10.2 落到代码上的四条规则

1. **输入路径上的任何调用都必须有"放弃"路径。**
   `SendInput` 没有任何超时参数——这是它最危险的地方。所以规则不是"给它设超时"，而是**永远不在可能被等待的上下文里调用它**（即钩子回调内），并且调用方**不等待结果**。
2. **推迟有时间上限，到点就放手。**
   推迟松手已经有时长上限（`RELEASE_DELAY_MAX_MS` 200 ms）。v2 再加一条：重放处于 `IN_FLIGHT` 超过 200 ms 就强制回落 `NONE` 并放行后续事件，宁可丢一次补发，也不把状态挂死。
3. **任何补发都不许无限重试。**
   一次，失败就记账（诊断计数器），然后放手。
4. **阻塞型等待一律禁用。**
   钩子回调内已有的纪律（只碰内存）扩展到整个输入路径：不允许 `SendInput`、文件 IO、跨进程调用、`WaitForSingleObject`、锁的超时等待。

## 10.3 这条原则能防住什么

- **本次事故**：钩子在等自己的注入 → 违反规则 1 → v2 修掉
- **未来任何"在回调里顺手做点事"的改动**：违反规则 1/4 → 由 §9.8 的结构守门在开发期就拦住
- **注入线程/定时器本身出问题**：违反规则 2/3 → 超时回落，最多丢一次补发

**防不住的**：已经陷进内核的线程。那只能靠"不要进去"，或者重启。
