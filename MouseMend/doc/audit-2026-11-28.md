## 二、驳回：四条看起来严重、实际不成立

**判断依据都是源码逐行核对，不是"我觉得"。**

1. **"三份文档说配置存 ini，代码只写注册表"**（乙 A4）。**这是我自己给评审的提示词写错了**。
   仓库只有一份 `README.md`，里面写的是 "the only thing it ever writes are its own settings
   in the registry"——文档与代码一致。记在这里是因为**错误的前提会生出错误的结论**：
   评审团拿到的前提错了，结论再漂亮也不能用。

2. **"注入的松开不更新 `system_down`，会造成卡键"**（甲 P0-1）。反了。`debouncer.c:498` 的
   条件是 `!data->system_down`——`system_down` 为真时那次松开是**放行**的（代码注释 485-493
   正是解释这一点）；注入失败时 `system_down` 保持为真，恰好描述了"系统仍按着"，下一次
   真实松开会被放行，不会卡。

3. **"双触点保护在结构上不可能成立"**（甲 P0-2）。它推演的序列 `DOWN1 过 → DOWN2 拦 →
   UP2 放行 → DOWN3 过 → UP3 被吞`，第三步之后 `isBlocked` 已被清空，UP3 不会再被吞。
   而"UP3 被吞"只在 DOWN3 也被拦时发生——那时 UP2 已经抬起了按钮，吞掉 UP3 没有代价。

4. **"阈值拦截隔一次放一次，抖动有一半漏过去"**（甲 P0-3）。每次 **按下**都在阈值内就被拦，
   漏过去的只有 `UP2`——而它是唯一一次能把 `DOWN1` 抬起来的事件，不放行才会卡键。
   从桌面看仍然是"一次点击"。

另外两条核对后不成立：`context_store` 的迁移长度检查（当前常量下不越界，已记入延期清单）；
`settings_window` 的字体泄漏（`WM_DESTROY` 删除并置 NULL，`WM_INITDIALOG` 不会在同一
HWND 上跑第二次）。

## 三、延期（记录理由，不在发版前动）

| 项 | 为什么现在不做 |
|---|---|
| `main.c` 2765 行、钩子回调与窗口过程零单测（乙 A1） | 这是**真的**最大结构性风险，但拆分要动钩子回调的调用栈，发布前做等于把最危险的一段重写一遍。**列为 2.6 的第一个重构项**，先补"回调 → 决策"的纯函数测试再拆 |
| `core` 反向依赖 `ui`（`app_controller` include `language.h`）（乙 B1） | 一行改动的表象，实际要动语言状态的所有权；与发版无关 |
| 暂停剩余时间在两处各算一遍（乙 B2） | 两处逻辑目前一致，收敛是改善不是修 bug |
| 日志目录优先 exe 同级，受 UAC 虚拟化影响可能"看不到"（乙 A6） | 现状有回落与提示；改成 `%LOCALAPPDATA%` 是行为变更，要单独一轮验证 |
| `autostart` 用 `MAX_PATH`（乙 B4）、诊断包 `exe_path[MAX_PATH]`（丙 P1-8） | 只在 >260 字符安装路径下发生；报告里只打印文件名，影响是"位置分类可能判错" |
| 学习采纳的 `shown[]` 抄了菜单一份（乙 B5） | 当前两边一致，缺的是机制而非缺陷 |
| 保存失败的两层去重（乙 B6） | 行为正确，只是状态放在 `static` 里不干净 |
| zip 32 位偏移（丙 P1-6） | 单附件上限 2 GB，现实触发不了 |
| 日志目录可能落在多用户可读位置（丙 P2-10） | 内容只有"时间+按钮+阈值"，不含程序名与坐标；属加固 |
| 乙的 C1–C5 | 已核验项与纪律边界记录，无动作 |
