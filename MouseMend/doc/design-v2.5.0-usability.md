## 2. 逐项方案

### 2.1 诊断补四类（#1）—— ✅ 已完成 `9b0d2d1`

> **实施时修订了落点**：原方案写"给 `--diagnose` 补四类"，**实际做不到**。
> `--diagnose` 是启动开关，在 `main` 里执行于**引擎初始化之前**（`main.c:2530`），
> 那时 `g_app` 根本没跑起来，它只能看到配置。
>
> 改成补进**诊断包**（菜单导出 / 崩溃时写入），那里 `CollectSupportReport`
> 能拿到全部运行时状态。`--diagnose` 保持只报配置，这是它的定位。

**现状**：`--diagnose` 输出 18 项，缺的都是"出问题时最想知道的"。

**要补的四类**：

| 字段 | 数据来源 | 为什么重要 |
|---|---|---|
| `context_paused` + 剩余分钟 | `context_filter_is_paused` + `pause_until` | 用户报"没拦住"，第一怀疑是暂停还没结束 |
| `advice_count` | `learning_service_snapshot` + `learning_advice_visible_count` | 判断"学了没" |
| `foreground` | `context_filter.snap` 当前槽的 `name` | 判断"是不是这个程序被排除了" |
| `caps_hook/learning/context/log` | `app_capabilities` | 现在只有汇总 `status`，不知道哪个模块死了 |

**落点**：`main.c` 的 `diagnostics_build` 调用点（`--diagnose` 分支）增加四个 `append`。

**验证**：`--diagnose` 输出多四行；`diagnose.ps1` 的键白名单要同步加，否则新键没人测。

> **坑**：`diagnostics_build` 自己 `debounce_init` + `settings_load`，与 `g_app` 无关。
> 所以它拿不到这些运行时状态，**必须让调用方传进去**（`--diagnose` 分支在 `main` 里，能拿到 `g_app`）。
> 这一点 2026-11-27 的审计已经踩过一次，不要再走弯路。

### 2.3 状态灯：3px 透明间隙归左块 + 收起变慢（#3）

> **2026-11-28 交互模型已更换：悬停展开 → 单击展开。** 本节写的间隙归属仍是当前实现，
> `CLOSE_MS = 0` 也仍然成立；变的只是"谁来触发展开"。真实使用证明悬停这条路无法做
> 到"丝滑"，原因与取舍见 §10.6。**本节保留原文**，因为它是缝隙与收起的依据。

**问题**：鼠标扫过两块之间的间隙时 `strip_hover` 变成 -1，**所有块一起收起**，然后进入下一块又全部展开。用户描述为"弹来弹去"。

**方案：视觉分隔与命中区域解耦**。

```
[paint 0][3px][paint 1][3px][paint 2]...
        ↑ 3px 是对话框背景色，视觉上仍是分开的
[hit 0──────][hit 1──────][hit 2──────]...
        ↑ 3px 归左边块，屏幕上没有无主像素
```

**落点**（`settings_window.c`）：

```c
// 当前：一个矩形既画又判
blocks[i] = { x, top, x + width, bottom };

// 改为：两套矩形
paint[i] = { x, top, x + width, bottom };          // 画背景和文字
hit[i]   = { x, top, x + width + GAP, bottom };    // 只用于 PtInRect
x += width + GAP;
```

- `FillRect` 和 `draw_centered_text` 用 `paint`
- `status_strip_hit` 用 `hit`
- **最后一块的 `hit` 等于 `paint`**（它右边没有缝）

**为什么不用"3px 画成左边块的颜色"**：那会让块的实际宽度多 3px，文字居中要再减回来，
多一层补偿就多一个出错点，而且视觉上"块变宽了"不是想要的效果。

**第二处：收起比展开慢（修订后作废）**。

初稿写的是"展开 0.14、收起 0.06"，**那是基于旧实现**。当前代码早已不是指数逼近，
而是固定时长线性：

```c
#define SETTINGS_STATUS_OPEN_MS  100.0f
#define SETTINGS_STATUS_CLOSE_MS   0.0f     // 收起瞬时
```

**而 `CLOSE_MS` 必须是 0**，理由记在 `handover-2026-11-26.md` §20.1：

> 块 i 的左边界 = 前面块当前宽度之和。收起只要还有动画，后面所有块就被一路带着
> 左移，看起来就是"先向左再向右"。

**所以"光跟着走"的手感做不到，也不该做**——它和"块位置由前块宽度决定"这个布局
前提直接冲突。

**主诉（弹来弹去）完全由第一处解决**：`hit` 永远有主人，`strip_hover` 不会变成 -1，
`status_strip_tick` 里那个 `(strip_hover < 0 && i == 0)` 的兜底分支在鼠标位于条上时
根本不会触发，**也就没有"全收再开"这个动作**。

**结论：这一处不改代码，`CLOSE_MS` 保持 0。**

**`SETTINGS_STATUS_GAP` 从 2 改成 3**。

**第三处：暂停时主块要说实话**。

现在暂停过滤时，主块仍显示「鼠标防护中」，**这不准确**——过滤实际是关着的。
主块是唯一常驻可读的锚点，不能在最需要它的时候说错话。

| 情况 | 主块文字 | 底色 |
|---|---|---|
| 正常 | `鼠标防护中` | 绿 |
| **暂停中** | **`已暂停 · 剩余 4:32`** | **黄** |
| 有问题 | `鼠标防护异常` | 红 |

剩余时间从 `context_filter` 的 `pause_until` 算，**每秒刷新**（现有 400ms 定时器够用）。

**不加第 6 个状态灯**：暂停是全局状态，属于主块；加块会把本来就窄的条切得更碎。

**验证**：真机截图三态 + 手工来回扫 20 次，确认没有"全收一下"；暂停后主块变黄且倒计时。

### 2.5 六个单选项 + 波纹标记（#5）—— ✅ 已完成（**没有加宽**）

#### 2.5.1 实测把"加宽"这一整块取消了

**原方案**：估算六项要 248 DLU、可用 223，差 25，于是加宽分组框 33 DLU、窗口 477→510，
右侧整组 x 全部 +33。**方案自己写了"必须实测、不要按估算写死"——实测之后，加宽这件事不需要了。**

实测方法（`doc/tmp/tmp_measure_labels.ps1`，不进库）：启动真实进程 → 找到体检窗口 →
用**它自己的控件**当标尺（`IDC_STATUS` 在 `rc` 里是 396 DLU，屏幕上是 693 px ⇒ 1 DLU = 1.75 px，
反算 `IDC_FILTER_AUTO` 恰好回到 44 DLU，误差 0）→ 用同一字体（Segoe UI 9pt @96 DPI）
量六个标签的像素宽 → 换算成 DLU。

| 标签 | zh | en | 取大 + 16 DLU 图标与留白 |
|---|---|---|---|
| 全部 / All | 15 | 8 | 31 |
| 左键 / Left | 15 | 12 | **31** |
| 中键 / Middle | 15 | 22 | **38** |
| 右键 / Right | 15 | 16 | **32** |
| 侧一 / Side 1 | 15 | 18 | **34** |
| 侧二 / Side 2 | 15 | 18 | **34** |

**合计 200 DLU + 5×4 间距 = 220**，而分组框内有 **230** 可用。最紧的一档**不在同一个语言里**：
`Middle`（22）压过 `中键`（15），而 `Side 1`（18）压过 `侧一`（15）。原估算按中文算、
还把每个字记成 12 DLU，两处都偏大，于是得出了"差 25"。

**结论：窗口 477×311 一个像素没动，右侧整组、状态灯、状态栏、`IDC_FILTER_HINT` 全部原位。**
这不只是省事：加宽要重排 20 个 `x` 坐标，是本轮最大的回归来源，而它现在变成了"零"。

> **"键"字：主键加、侧键不加，两轮才定下来。** 第一版为了省宽度写成 `左`/`侧一`
> （合计 217），用户看截图后说"不省那个键字也放得下"——重量确认：`左键` 15 DLU 让三项
> 各 +7，但 `中键`/`右键` 仍被英文压住，总共只多 7 DLU。**侧键则反过来**：用户要求
> 和测试区环里写的字一致，于是定成 `侧一`/`侧二`。
>
> 顺带排除的两种写法，都给后来人省一次试错：`侧键一` 4 个字 23 DLU，两项 +6，
> 合计 224 挤到没有余量；`侧键 1`（带空格）20 DLU，宽度没问题，但和环里的 `侧一`
> 不一致——**同一个窗口里描述同一个按键的两个地方，用词不能不一样**。

实际写进 `rc` 的六个控件（y 全是 29，与原来一致）：

| 控件 | x | 宽 | 累计右边界 |
|---|---|---|---|
| `IDC_FILTER_AUTO`（全部） | 14 | 31 | 45 |
| `IDC_FILTER_LEFT`（左键） | 49 | 31 | 80 |
| `IDC_FILTER_MIDDLE`（中键） | 84 | 38 | 122 |
| `IDC_FILTER_RIGHT`（右键） | 126 | 32 | 158 |
| `IDC_FILTER_X1`（侧一） | 162 | 34 | 196 |
| `IDC_FILTER_X2`（侧二） | 200 | 34 | 234（框内到 414 px / 237 DLU） |

**`rc` 里那行注释写了"宽度是量出来的"**：谁要改这六个字符，必须重量一次。

> **踩坑一：`MapDialogRect` 不能跨进程调。** 方案原话是"用 `MapDialogRect` 量"，
> 但从脚本里对别人的对话框调用它，**直接把 PowerShell 打死**（`0xC0000005`）——
> 对话框把自己的映射状态存在自己的进程里。改用"已知 DLU 宽度的控件当标尺"，
> 反而更可信：它是这台机器、这个 DPI、这个字体下的真实比例。

**"滚轮并入中"是 UI 层合并，不是数据层合并**：`debouncer` 仍按三个键分别判定，
筛选只是把三个键的显示条件都指向"中"这一项。

**筛选判定的真实落点**（`settings_window.c:126`），现在只有一行：

```c
return window->filter_auto || (entry->button == window->filter_button);
```

改成：

```c
// "中" also covers the wheel: they share one physical control, and a user who
// selected "middle" means "the middle button and its wheel", not "middle clicks
// only, wheels invisible". The engine still treats them as three independent
// buttons - this is a display filter, not a merge.
static bool entry_is_visible(const SettingsWindow *window, const TraceEntry *entry)
{
    if (window->filter_auto)
        return true;

    if (window->filter_button == MOUSE_BUTTON_MIDDLE)
    {
        return entry->button == MOUSE_BUTTON_MIDDLE ||
               entry->button == MOUSE_BUTTON_WHEEL ||
               entry->button == MOUSE_BUTTON_HWHEEL;
    }

    return entry->button == window->filter_button;
}
```

**落地方式：一张表，三处共用。** 原方案说"另外三处必须一起改"，实际做法是把
`control / button / tip` 三样一起放进 `FILTER_BUTTONS[]`，标签、启用与勾选状态、点击处理
全部走这一张表。**同一份名单抄三遍，迟早有一份没人看的那份先烂掉。**

| 位置 | 现在是 |
|---|---|

#### 2.5.3 波纹标记：方向是事件的属性，不是按键的属性

**方案这里有个前提错误，是实施时才发现的。** 方案写的表是"上滚 → `上`、下滚 → `下`"，
照字面读会以为 `MOUSE_BUTTON_WHEEL` 和 `MOUSE_BUTTON_HWHEEL` 对应上/下。**不对**：
`HWHEEL` 是**横向**滚轮（"横滚"），上下两个方向都属于 `WHEEL`，只能靠 `data` 的正负区分——
这正是方案自己要求加 `TraceEntry.data` 的原因，两句话在方案里互相矛盾。

所以最终做法：

| 事件 | 环里的标记 |
|---|---|
| 左 / 中 / 右 | `左` / `中` / `右`（en `L` / `M` / `R`） |
| 侧1 / 侧2 | `侧一` / `侧二`（en `X1` / `X2`）——数字会被误认为计数 |
| 上滚 / 下滚 | `上` / `下`（en `↑` / `↓`），由 `data` 的符号决定 |
| 横滚 | `横`（en `H`）——**不画左右箭头**：它们和左右键的标记撞车，而横滚是稀有设备 |

- **`BUTTON_MARKS` 里 `WHEEL` 故意留空**：`lang_button_mark()` 仍返回空串，环里改用
  `lang_scroll_mark(data)`。标记从"按键的属性"变成"事件的属性"，只有滚轮这一条走另一条路。
- `TraceEntry` 加了 `int32_t data`，`main.c` 在 `event_trace_push` 之前补 `entry.data = event->data`。
  `event_history` 是整条拷贝，跟着一起有了。
- `ripple_view_color`：X1 青、X2 紫；两个滚轮都用中键的绿——**同一个物理控件**，
  方向交给标记说。颜色是第二线索，标记才是第一线索。
- **滚轮现在会画环，而以前不会**（原来只对 `is_down && !wheel` 触发）。高分辨率滚轮一次
  手势会报几十个事件，所以按"同一个轮子的环还在屏幕上就不再起新的"节流；换方向是另一个
  button，立刻给新环。**这是本轮唯一新增的节流规则，理由写在 `trigger_ripple` 里。**

#### 2.6.2 实时日志

**关键判断：复用 `EventHistory`，不新建体系。**

`TraceEntry` 已经有 `button` / `timestamp` / `x` / `y` / `is_down` / `decision`，

**要做三件事**：

1. `TraceEntry` 加 `wchar_t process[32]`
2. 钩子侧填它——**在已有的 `context_filter_should_suppress(&snap, ...)` 旁边**，

3. 窗口里加一个只读多行 EDIT，格式沿用测试日志的表头

> #### 程序名归属：实施前必须先接受的已知限制（2026-11-28 补）
>
> **事实**：`context_service` 是 **300 ms 轮询** `GetForegroundWindow`（`CONTEXT_POLL_MS`），
> 而"点击让窗口成为前台"发生在**点击之后**。所以点击一个原本不在前台的窗口时，
> 钩子那一刻读到的槽里仍是**上一个**程序 —— 日志第一行会记到旧程序名下，
> 之后轮询更新、才写出切换分隔行。
>
> **不能在钩子里当场解析**：`GetForegroundWindow` / `WindowFromPoint` 是 user32 调用，
> 钩子回调有硬性时间预算（超了会被系统静默摘钩），这条路线直接排除。
>
> **决定（建议，实施时照此执行）**：
> 1. **记"判定所用的那个名字"，不是"屏幕上真实的那个程序"**。日志的职责是解释判定，
>    而判定确实用的就是这个槽 —— 两者一致才解释得通。
> 2. 同时把 `slot->pid` 一起记进 `TraceEntry`（`int32_t pid`），**先不上屏**。
>    将来若要按真实前台重新解析，数据已经在手上；现在不加，以后要同时改三处推送点。
> 3. 由此产生的"切换后第一行归旧程序"是**已知限制**，必须写进
>    `event_trace.h` 的字段注释和 `main.c` 的填充处（项目规则：已知未修写进源码，不能只写日志）。
> 4. 分隔行只在名字变化时写，所以错误归属最多影响切换后的第一行，不会蔓延。
>
> **不要**为了"更准"改成"每次点击都查一次进程名"：那是在钩子线程上做 OpenProcess/查询，
> 是这套架构从 1.x 起就在守的那条线。

**段标签只写程序名，不写"已切换到"**。方案写的是 `—— 已切换到 notepad.exe ——`，
那是按时间正序想的；实际最新在上，标签在它所描述的行的**上方**，读起来是一个小标题。

- 找到松开 → 填实测毫秒；

- 超过引擎的配对超时（`SETTINGS_CLICK_EXPIRE_MS` = 2000 ms）仍没有松开 → `>2000`，
  **明确是下界**，不是数字。测试日志用同一句话表示"松开丢了"。

（`context_filter_publish(..., ours=true, L"")`）——状态栏按 `ours` 标志判断，看不出问题，
但实时日志会显示"未知程序"，偏偏这是唯一一个不可能未知的程序。改成启动时解析一次

#### 2.6.3 隐私：坐标不显示

`TraceEntry` 的 `x` / `y` **已经有了，但从来只用于波纹定位，不上屏**。

**数据不落盘**：`EventHistory` 和 `EventTrace` 都是内存环形缓冲，写盘只有拦截日志

#### 2.6.5 为按程序分池留基础

**不用改数据流**。反过来，如果现在不加这个字段，将来要改 `event_trace`、
`event_history`、钩子回调三处。

### 10.6 状态灯改为单击展开（2026-11-28，**推翻 §9 的一条"明确不做"**）

#### 先说原来的决定是怎么来的

不是随手选的：**悬停展开是 2026-11-26 用户自己提的形态**
（`handover-2026-11-26.md` §19：「鼠标滑过时悬停块加宽，直到文字完整显示，移开回到五个
方块」）。当时连带定下两条，今天**都保留**：

- 缝隙的绘制与命中解耦（缝是背景色、命中归左块），否则指针在缝上会 `hover = -1`；
- `CLOSE_MS` 必须是 0（§20.1：块 i 的左边界 = 前面块宽度之和，收起有动画会把后面的块
  一路带着左移）。

§19.7 还把"方块里有单字，**滑上去即可确认**"当作低对比度配色可以被接受的理由。
所以这次改动不是"觉得悬停不好看"，而是**那条可读性依据在真机上不成立**。

#### 为什么必须换（三条都是实测，不是推测）

1. **目标会被自己的展开推走**。块的左边缘是前面所有块的宽度之和，所以展开哪一块，
   它右边的块全部右移。指针指向的块在靠近过程中一直向右跑，停在哪取决于动画进行到
   哪一帧 —— 这不是缓动曲线能修的，是布局前提决定的。
2. **暂停时宽度还会自己变**。块 0 显示 `已暂停 · 剩余 4:59`，不同数字的宽度不完全相同，
   于是右边四块的命中矩形每秒都可能动一次；指针下面会"自己换块"。
3. **缝的滞留**。指针每次跨块都要经过 3 px 的缝，那几毫秒里高亮先落到左边块再跳到右边，
   读起来就是"弹"。

#### 改成了什么

| 行为 | 旧 | 新 |
|---|---|---|
| 展开触发 | 指针悬停 | **单击**（点已展开的块 → 收回总览块） |
| 悬停效果 | 加宽 + 提亮 | **只把该块的字符提亮**（35% → 85% 白），宽度不变 |
| 指针形状 | 箭头 | **手型**（`WM_SETCURSOR` + `IDC_HAND`），这是 21 px 方块唯一放得下的"可点击"暗示 |
| 提示 | 无 | **两行**：块 caption + 「点击展开 / 点击收起」 |
| 暂停倒计时 | 宽度随数字变 | **按最长形态（`720:00`）预留宽度**，整段暂停期间一个像素都不动 |
| 静止态 | 块 0 展开 | 不变（**永不退回五个匿名方块**，见 §19.1） |
| `CLOSE_MS` | 0 | 不变，理由见 §20.1 |

#### 为什么不是其它几个方案

- **"停留 80 ms 才切换"**（§2.3 的备选）：它只减少切换次数，改不了"目标被推开"这个
  几何事实 —— 指针停在原地不动时，展开动画照样把目标从它下面移走。
- **收起也给动画**：正是 §20.1 明令禁止的那一种，指针下的块会先左后右。
- **让块不占宽度、改用浮层显示文字**：等于换掉整个控件形态，§19 的"五块一条"就没了，
  而且悬停浮层会盖住相邻块。
- **保持悬停但降低动画时长**：延迟变短只会让"跳"更快，不会变顺。

#### 代价

- 少了一次"扫一眼就知道每块在说什么"的路径，改用**提示 + 单击**两步。这是可接受的原因：
  静止态的颜色本身就是状态（绿/琥珀/深色），文字只是解释。
- 新增两条文案（`STR_STRIP_TIP_EXPAND` / `_COLLAPSE`）和一处 `context_filter.h` 的依赖
  （为了 `CONTEXT_PAUSE_MAX_MINUTES` 这个上限，避免第二次硬编码 720）。

#### 验证（脚本，不进库）

`doc/tmp/tmp_strip_click.ps1` 用 `PrintWindow` 读像素、`PostMessage` 驱动：

```
resting : verdict block width = 79
hover moves nothing : True
paused  : amber width 124 -> 124 after 1.4 s   （倒计时在走，宽度不动）
geometry stable while counting : True
click   : clicked x=116, block 3 width 82 at x=48
```

五项断言全过。**"点下去好不好看、提示文字会不会被裁"仍需一眼**，这部分没有可读文本。

#### 实施时踩到的坑：`TTF_SUBCLASS` 本身就是一层子类（`45b149e`）

`TTF_SUBCLASS` 不是"让提示自己盯着鼠标"，而是**给控件再加一个子类**。子类按后装先跑
的顺序执行，所以 `status_strip_subclass` 先拿到 `WM_MOUSEMOVE`；它当时 `return 0`，
等于告诉系统"已处理"，提示永远收不到指针移动 —— **一次也不会出现**，而且不会有任何
报错。

修法：处理完 `break`，让 `DefSubclassProc` 继续往下传（`WM_MOUSELEAVE` 与
`WM_LBUTTONUP` 同理；`WM_SETCURSOR` 仍然直接返回 TRUE，手型要盖过 static 自己的箭头）。
**这条对任何"自己子类化 + 同时要 tooltip"的控件都成立。**

### 10.7 展开态的"退出"：三个时机，没有定时器（2026-11-28 晚）

用户提了两个想法：**（a）三分钟没点任何色块就自动收回总览；（b）点其他非色块区域就收回。**
（b）采纳（按下面的白名单实现）；（a）**没有做**，理由记在这里。

#### 为什么不做定时器

- **它会自己动**。这正是这一轮刚赶走的东西：悬停方案的问题就是"没人操作，行内却在动"。
  三分钟后自己收回，用户正在读的那一段会当着面消失，和"闪烁/跳动"是同一类体感。
- **三分钟是任意值**。用户自己也没坚持；一个没有语义的门限，只会在某天被改成两分钟。
- **它想解决的问题已经解决了**。不点它就不会跑的担心，真正来源是"我离开了，回来看到
  一个忘了为什么展开的东西"——那由"收进托盘就复位"解决，而且**用户看不见它复位**。

#### 真正的三个出口

| 何时 | 怎么实现 | 用户看得到吗 |
|---|---|---|
| **点别的地方**（换了件事做） | `WM_COMMAND` 来自非色块控件 → 复位 | 看得到，但是自己按的，等于抽屉被关 |
| **点对话框空白处** | 对话框的 `WM_LBUTTONDOWN` → 复位 | 同上 |
| **把窗口收进托盘** | `hide_to_tray()` 里直接把 `strip_pinned` 置 0 | **看不到**：窗口已经消失 |
| 点已展开的块 | 回到总览（原有行为） | 看得到 |

"点别的地方"有一个**白名单**：三个只读窗格（`IDC_TESTLOG` / `IDC_BLOCKLOG` / `IDC_DIAG`）
和自绘测试区（`IDC_RIPPLE`）不算"换了件事"。点进日志里选一行、或者去测试区点几下，
都属于"还在看同一件事"，把行收起来会让人以为自己点错了。

#### 踩到的坑：`WM_PARENTNOTIFY` 这条常规路线走不通

第一版把"点了子控件"挂在对话框过程的 `WM_PARENTNOTIFY` 上，**真实点击刷新按钮毫无反应**。
两点实测结论：

1. 该消息**不会交给对话框过程**（把处理放进 DlgProc 里，真实点击无效；放进对话框子类里
   也无效）——所以"子类化对话框"这条补救也不用试了；
2. **跨进程 `PostMessage(WM_PARENTNOTIFY)` 直接返回 FALSE**（它是系统消息，不允许外部
   进程伪造），所以连"模拟验证"都不成立。

改成 `WM_COMMAND` 就通了：按钮、单选项、编辑框（`EN_SETFOCUS`）都会发它，而这三类
恰好就是"用户去做了别的事"的全部来源。分组框/静态文本点了没有命令，也不该复位。

#### 验证（`doc/tmp/tmp_strip_click.ps1`）

```
reset : after click=21  bg-click=79  other-ctrl=79  reopen=79
CHECK click on dialog folds it back .... True
CHECK click on other control folds ..... True   （真实点击刷新按钮，不是 PostMessage）
CHECK reopen starts at the verdict ..... True
```

### 10.8 六个筛选：加宽被实测取消，滚轮方向不是按键的属性（2026-11-28）

§2.5 落稿时有三处是推算，实施时全被事实推翻。记下来，因为它们都属于
"照方案直接动手就会做错"的那一类。

**① 加宽整块取消。** 方案估 248 DLU / 可用 223 → 决定加宽 33 DLU、窗口 477→510、
右侧所有 x +33。实测 220 DLU / 可用 230，装得下（第一版短标签 217、带"键"的中间版本
224，最终定稿 220）。两处估算偏大：把每个中文字记成
12 DLU（实际 Segoe UI 9pt 下是 7.5），且只按中文算（最紧的是英文，"Middle" 22 DLU）。
于是本轮最大的回归源（重排 20 个 x 坐标）**一次都没碰**。方案自己写了"必须实测、
不要按估算写死"，这条救了自己。

**② 波纹方向属于事件，不属于按键。** 方案表写"上滚 → 上、下滚 → 下"，照字面会以为
`WHEEL`/`HWHEEL` 对应上下；实际 `HWHEEL` 是横滚，上下都在 `WHEEL` 里，只能看 delta 的
符号——而方案另一段又在要求给 `TraceEntry` 加 `data`，理由是"否则分不出上下"。
两句话互相矛盾，实施时以"标记由事件决定"为准：`WHEEL` 在标记表里**故意留空**，
环里改问 `lang_scroll_mark(data)`；横滚给固定的"横"，不画左右箭头（会和左右键撞车）。

**③ 滚轮开始画环。** 原来是 `is_down && !wheel`，滚轮永远没有环。现在滚轮也有，
但要节流：高分辨率滚轮一次手势报几十个事件，不节流就成了机关枪。规则是"同一个轮子
的环还在屏幕上就不再起新的"，换方向立刻给新环。

**两个新踩的坑（都会静默出错）：**

| 坑 | 现象 | 现在怎么做 |
|---|---|---|
| `MapDialogRect` 跨进程 | 从脚本对别人的对话框调用，**PowerShell 直接 0xC0000005**（对话框把映射状态存在自己进程里） | 改用"已知 DLU 宽度的控件当标尺"：`IDC_STATUS` 396 DLU = 693 px。反算另一个控件误差为 0，比 `MapDialogRect` 还好核对 |
| `PrintWindow` 对自绘 static | 直接印 `IDC_RIPPLE` 得到**全黑**（`SS_OWNERDRAW` 不处理 `WM_PRINT`），据此会误判"滚轮没画环" | 印**整个对话框**再裁那一块，与 `tmp_strip_pause.ps1` 对付状态灯的办法一致 |

**验证**：`doc/tmp/tmp_filter_row.ps1` 六项检查全 True（见 §2.5.4），
截图 `doc/tmp/shot_filter_row.png`；单测 3496 → **3550**；两平台 Release 含 `/analyze`

### 10.9 三块表统一、热区替代复选框、设置按钮占位（2026-11-28 晚，用户看图后提的）

**① 实时日志补上"按住"列。** 用户的理由是"三块表少一列看着奇怪"，这个理由比我的更硬。
第一版不做的说法是"一个事件不知道自己何时松开"——理由没错，**结论错了**：把同一按钮的

### 10.10 两处日志不重叠，但各自缺对方有的一半（2026-11-28 深夜）

用户的提问很具体：实时日志有没有保存？托盘「高级 → 打开历史记录目录」用的是不是它？
两者重不重复？有没有能优化的地方？**核实结果是：不重复，但两份材料各自缺一半。**

| | 实时日志（窗口右下） | 拦截记录（磁盘 `Log\YYYYMMDD.log`） |
|---|---|---|
| 来源 | `EventHistory` 内存环 96 条 | `block_log` 队列 → 文件 |
| 范围 | **全部**按键（通过 / 忽略 / 拦下） | **只有被拦下**的点击 |
| 字段 | 时间、按键、间隔、按住、判定、**程序名** | 时间、按键、按下/松开、阈值——**没有程序名** |
| 留存 | 进程退出即失；唯一出口是诊断包 | 按天分文件，永久 |
| 开关 | 一直有 | 托盘开关，默认关 |

所以两者不是"重复的两份东西"，而是"现在看"和"事后查 / 发给作者"两条路。
真正的问题是**信息差**：事后翻日志只有 `left pressed threshold=50ms`，看不出在哪个程序里点的；
而诊断包的 events 表有坐标、**没有程序名**——两边刚好互补，又都不完整。

**改了什么：**

① `BlockLogEntry` 加 `wchar_t process[BLOCK_LOG_PROCESS_CHARS]`，`block_log_push()` 多一个参数。
钩子里不做任何解析，只是把 `main.c` 已经读出的那份名字拷进槽位。**读一次、两个消费方共用**：
`TraceEntry` 和 `BlockLogEntry` 描述的是同一次点击，两次读可能跨过一次上下文更新而互相矛盾。
行格式是 `时间 \t 程序 \t 按键 \t 事件 \t threshold=Nms`，空名字写 `-`，保证每行都是五列。

② 诊断包 events 表加 `program` 列，表头改成**用同一套宽度格式化**（`"%8s  %-24s  …"`），
不再手打空格——手打的表头已经和行差了一列。

③ 文案：「历史目录」→「拦截记录」（窗口按钮）、「打开历史记录目录」→「打开拦截记录文件夹」
（托盘），读不到目录时的提示里那两处"历史记录"也改成"拦截记录"。**叫"历史"会让人以为
全部历史都在里面**，而它只装被拦下的点击。

④ 「清空记录」→「清空显示」，并给这个按钮和「拦截记录」各加一条悬停提示；
`CONTROL_TIPS[]` 从"筛选专用表"升格为通用表（原名 `FILTER_TIPS` 已经名不副实）。
清空**不动磁盘文件**这件事以前没有任何说明，用户很容易以为"清空"等于全清。

⑤ 目录落点的 UAC 问题**没有动**，但结论写进了代码：`block_log_resolve_directory()` 顶部的
DEFERRED 注释。关键事实是**本项目没有清单文件**，所以 32 位版本写 `Program Files` 会被
UAC 虚拟化到 `%LOCALAPPDATA%\VirtualStore\...`（写成功、文件存在、用户被告知的目录却是空的），
而 64 位版本从不虚拟化——**这正是测试时看不出来的原因**。留给 #6 的导出功能一起决定。

**三个坑：**

| 坑 | 现象 | 处理 |
|---|---|---|
| `small` 是 Windows 的宏 | `BlockLogQueue small;` 报"BlockLogQueue 后面接 char 非法"——`rpcndr.h` 里 `#define small char`（MIDL 遗留） | 变量改名，并在测试里写明原因 |
| 窄 `printf` 的 `%S` | 按 C locale 转换，`微信.exe` 会变成 `????.exe` | 程序名先 `to_utf8()` 再用 `%s`；截断按 UTF-8 字符边界（`utf8_truncate`），不在半个汉字上切 |
| 文件从纯 ASCII 变成可能有中文 | Excel 按 ANSI 码页读，中文乱码 | 新建文件写 UTF-8 BOM（在表头之前，跳过 `# ` 行的脚本不受影响） |
