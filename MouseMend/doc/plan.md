# 迭代方案（v1.2.0 时期，原名 MouseFix）

> **2026-11-22 更名**：产品已改名为 **MouseMend 2.0.0**（公司「梦创」，版权 `By_yao (C) 2026`）。
> 本文档正文里出现的 `MouseFix` 是历史名称，保留原样是因为它记录的是当时的决策过程；
> 当前名字、版本与来源以 `version.h` 为准。

> 本文档是实施依据。每条改动都先写清楚"为什么"，再写"怎么做"和"怎么验证"。
> 实施过程中如果发现与本文档冲突，先改本文档，再改代码。

---

## 0. 背景与目标

当前 v1.1.0 是一个 125 KB、纯 C、无第三方依赖的托盘程序。它已经能正确去抖，
但存在三个结构性问题，本轮全部解决：

| 问题 | 后果 | 本轮措施 |
| --- | --- | --- |
| 低级钩子被系统静默摘除后进程毫不知情 | 界面/菜单仍显示"防护已启用"，实际已失效 | 新增**死钩子看门狗**（M1） |
| 两处编辑入口（托盘菜单 / 新界面）会互相覆盖设置 | 用户改的值被静默回滚 | 新增**AppController 单一真源**（M2） |
| 界面上完全看不到"它到底做了什么" | 用户只能相信，无法验证 | 新增**设置窗口**：实时计数 + 点击测试区 + 自检（M3） |
| 拦截事件没有留痕，事后无法复盘 | 用户/支持无法判断哪天开始变严重 | 新增**拦截历史日志**（M4） |

顺序固定为 M1 → M2 → M4 → M3，理由：M1 修复的是"撒谎"，M2 是 M3 的地基，
M4 只依赖 M2，M3 是唯一有视觉风险的部分，放最后。

## M1 死钩子看门狗

### 为什么

`WH_MOUSE_LL` 在安装它的线程上执行。如果该线程被阻塞超过
`HKCU\Control Panel\Desktop\LowLevelHooksTimeout`（默认 300 ms），
**Windows 会把钩子从链上摘掉，并且不通知任何人**。
此时 `g_app.mouse_hook.installed` 仍是 `true`，菜单和 tooltip 会继续声称防护正常。
这是本产品唯一无法被用户察觉的失效模式。

### 怎么做

新增 `src/core/hook_watchdog.{c,h}`，纯判定逻辑，不含任何 Win32 调用：

```c
typedef struct {
    uint32_t last_system_input_tick;  // GetLastInputInfo().dwTime
    uint32_t last_event_count;        // 钩子回调计数
    uint64_t last_recover_tick;
    uint32_t recover_count;
    int suspect_streak;
    bool initialised;
} WatchdogState;

typedef enum {
    WATCHDOG_FIRST_CHECK,   // 仅记录基线
    WATCHDOG_ALIVE,         // 没有输入，或输入被我们看到
    WATCHDOG_SUSPECT,       // 有输入但钩子没看到（连续计数）
    WATCHDOG_RECOVER        // 确认异常：重装钩子
} WatchdogVerdict;
```

判定规则（`hook_watchdog_check`）：

1. 系统输入时间戳**没有变化** → ALIVE（用户空闲，无从判断）。
2. 系统输入变化 **且** 我们的计数也变化 → ALIVE，清零连续计数。
3. 系统输入变化 **但** 计数没变 → `suspect_streak++`。
4. `suspect_streak < WATCHDOG_SUSPECT_LIMIT`（2）→ SUSPECT（避免采样边界误判）。
5. 距上次恢复不足 `recover_cooldown_ms`（30 s）→ SUSPECT（避免抖动式重装）。
6. 否则 → RECOVER：清零 streak，记录时间与次数。

`main.c` 侧：

- 每 3 s 的 `TIMER_WATCHDOG`，读 `GetLastInputInfo` + 钩子事件计数。
- RECOVER → `mouse_hook_uninstall` + `mouse_hook_install`；失败则把
  `hook_ready` 置 false（界面/菜单/诊断立刻变"防护未生效"）。
- 恢复次数写入诊断报告（`hook_recoveries=`）。

### 误报与代价

UIPI 场景（用户在管理员权限窗口里操作）会让我们的钩子看不到输入 → 误判为死亡。
重装钩子的代价是极短的"未过滤窗口"，不影响正确性，且被限流到 30 s 一次。
判断：可接受，优于静默失效。

### 验证

- 单测覆盖全部 6 条分支 + 空闲、输入+事件、只有输入、冷却、恢复后再犯。
- `--diagnose` 增加 `hook_recoveries` 字段。

## M2 AppController 单一真源

### 为什么

托盘菜单目前直接改 `DebounceManager`，每次点击调用 `settings_save()` 同步写
18 个注册表值。加入第二个编辑入口（设置窗口）后：

1. 两个入口各自持有旧快照 → 后提交者覆盖前者的修改。
2. `清零拦截次数` 需要同步重置气泡基线，否则下一个气泡会报出巨大的数字。
3. `language_get()` 与 `prefs.language` 已经靠 `SaveSettings()` 里一行镜像勉强粘住。

另外，滑块拖动会以像素级频率触发 `WM_HSCROLL`，每次都写 18 个注册表值 →
UI 线程长时间阻塞 → 正好踩中 M1 要解决的钩子超时。

### 怎么做

新增 `src/core/app_controller.{c,h}`。它**借用**（不拥有）现有的
`DebounceManager` 与 `Preferences`，是所有修改的唯一入口：

```c
void app_controller_attach(AppController *, DebounceManager *, Preferences *);
void app_controller_set_save_sink(AppController *, AppControllerSaveFn, void *user);
void app_controller_set_threshold(AppController *, MouseButton, uint32_t);
void app_controller_set_monitored(AppController *, MouseButton, bool);
/* ... set_all_monitored / set_hybrid / set_release_delay / set_drag_distance
       set_language / set_notify_blocks / set_log_blocks / apply_preset
       reset_statistics ... */
void app_controller_touch(AppController *, uint64_t now);  // 标记脏 + 记录时间
bool app_controller_commit(AppController *);               // 立即落盘
void app_controller_tick(AppController *, uint64_t now);   // 到期才落盘
```

关键规则：

- 所有 setter **只改内存 + 标记 dirty + 通知 observer**，绝不碰磁盘。
- `app_controller_tick` 在 `now - dirty_since >= APP_CONTROLLER_COMMIT_DELAY_MS`（400 ms）
  时才提交；由 UI 线程的 200 ms 定时器驱动。
- 落盘通过**函数指针 sink** 完成，测试里换成记录器，因此不需要注册表。
- `set_save_sink` 使 `app_controller.c` 不依赖 `settings.c`，可在测试工程中独立编译。

### main.c 改造

- 菜单动作：`app_controller_set_*` + `SaveSettings()`（用户点一下就该立刻生效）。
- 设置窗口滑块：只调 setter，靠 `app_controller_tick` 防抖提交。
- `SaveSettings()` 内部改为 `app_controller_commit()`，并保留"注册表不可写时一次性告警"。
- `reset_statistics` 走 controller，由它同时重置气泡基线。

### 验证

- 单测：脏标记、延迟提交、连续 setter 只提交一次、sink 失败时保持 dirty、
  清零统计同时重置 notify 基线。

## M3 拦截历史日志

### 为什么

用户想知道"是不是最近越来越严重"。日志是唯一能回答这个问题的东西。

### 位置与命名

```
<exe 目录>\Log\YYYYMMDD.log
```

- 目录与 exe 同级 → 用户看得见、能自己删（这是用户明确要求的语义）。
- 若 exe 目录不可写（Program Files），回退到 `%LOCALAPPDATA%\MouseFix\Log`，
  并在诊断报告的 `log_dir=` 里显示真实路径，避免用户找不到。

### 开关语义（用户明确要求）

- 默认**关闭**，菜单位置：`高级设置 ▸ 记录拦截历史`。
- 用户删掉整个 `Log` 目录 → **选项保持开启**；下一次真的发生拦截时，
  自动重建目录与当天文件（每次写入前 `CreateDirectoryW`，忽略已存在）。
- 没有拦截事件时**不产生空文件**。

### 行格式（ASCII，便于 grep / 导入 Excel）

```
2026-11-21 15:04:03.123	left	pressed	threshold=50
```

字段：本地时间（毫秒）\t 按键 slug \t 事件类型 \t 当时阈值。
按键 slug 固定英文（`left/right/middle/x1/x2/wheel/hwheel`），
**不随界面语言变化**，否则同一份日志会出现两种键名。

### 绝不在钩子回调里做文件 IO

新增 `src/core/block_log.{c,h}`：

- 固定 64 项的**环形缓冲** + 临界区，钩子回调里只做 `block_log_push`（内存写）。
- 推入后 `PostMessage(WM_APP_LOG_FLUSH)`，由 UI 线程批量 drain 并写文件。
- 环形缓冲满时丢弃最旧的一条并计数，诊断报告输出 `log_dropped=`。

时间换算：启动时记录 `base_tick = GetTickCount64()` 与 `base_local = GetLocalTime()`，
条目只存 `elapsed_ms`，UI 线程用 `FILETIME` 相加还原绝对时间。
这样钩子回调里不需要任何时间 API 调用。

### 验证

- 单测：环形缓冲的先进先出、满时丢最旧、格式化的日期滚动（跨天换文件）、
  行格式、slug 与语言无关。
- 端到端：开关持久化；关闭时不建目录。

## M4 设置窗口

### 为什么

用户需要"自己验证它有效"，而不是相信文案。

### 技术选型

**Win32 DIALOGEX + comctl32**，理由：

| 方案 | 代价 |
| --- | --- |
| **✅ DIALOGEX + comctl32** | +约 10 KB，纯 C，保留单文件、无障碍、高对比度 |
| 自绘/Direct2D | 控件无 HWND，UIAutomation / 键盘 / 屏幕阅读器全要手写 |
| Dear ImGui | 需要 C++，+400 KB，无原生无障碍 |
| WinUI3 / WPF | +50~150 MB，摧毁"单文件免安装" |
| WebView2 | 依赖外部运行时，初始化在 UI 线程，正踩钩子预算 |

### 第一版内容（只读为主，零落盘风险）

| 控件 | 说明 |
| --- | --- |
| 实时计数 | 7 行 `左键：9 次`，250 ms 刷新，只显示有拦截的键（为空时提示"还没有拦截到误触"） |
| 点击测试区 | 显示"本窗口打开后：收到 N 次点击，拦截 M 次"，用户随便点就能看到它在工作 |
| 自检报告 | 只读多行 EDIT，内容与 `--diagnose` 一致，带"刷新"按钮 |
| 打开日志目录 | 仅当历史日志开启时可点，打开资源管理器 |

**不含**滑块：留到下一轮，因为滑块需要标签联动与 DPI 校验，风险高于收益。

### 窗口生命周期

- 单例：重复打开只 `SetForegroundWindow`，不新建。
- 关闭 = `DestroyWindow`，不退出进程。
- 250 ms 定时器只在窗口存在期间运行（`WM_INITDIALOG` 建、`WM_DESTROY` 杀）。

### DPI 处理（本轮不做，明确记录）

项目没有 manifest，进程级为 DPI 虚拟化。设置窗口使用 DLU + Segoe UI 9，
在 150% 缩放下会被系统整体放大（略模糊但尺寸正确），与现有输入框一致。
切到 Per-Monitor V2 需要同时改输入框的字体与布局，作为独立任务，本轮不做，
避免只改一半造成输入框在高 DPI 下变小。

### 验证

- 编译期：四配置零告警 + `/analyze`。
- 运行期：`tests/smoke/gui.ps1` 打开窗口、校验存在、关闭；
  `--diagnose` 保证核心状态可读，即使 GUI 出现视觉问题也不影响判断。
- 视觉：由用户在本机确认（无法自动断言像素）。

## 实施记录（完成后的复盘）

### 实际落地与计划的偏差

| 项 | 计划 | 实际 | 原因 |
| --- | --- | --- | --- |
| M4 设置窗口 | 实时计数 + 测试区 + 自检 | 同计划，**额外**加了"打开历史目录"按钮 | 历史开关做出来后，缺一个入口会显得断裂 |
| M4 滑块 | 留到下一轮 | 保持留到下一轮 | 与计划一致：滑块需要标签联动与 DPI 校验 |
| M3 日志 | 环形缓冲 64 项 | 同计划 | — |
| 看门狗 | 3 s 周期、30 s 冷却 | 同计划 | — |

### 实施中被测试抓到的三个真实缺陷（值得记住）

1. **控制器挂接顺序错误**（被 `e2e.ps1` 抓到）
   `InitializeApp` 里先 `ApplyPreset(...)` 再 `app_controller_attach(...)`。
   因为预设现在走控制器，而控制器尚未挂接 → 预设静默失效 → 首次运行所有阈值是 0。
   **教训**：把"直接改状态"改成"必须经某层"时，要检查该层在所有调用点之前是否已就绪。
   修法：`attach` 提前到 `debounce_ready` 之后、第一个预设之前。

2. **宽字符串里的 `%s` 配 `char*`**（被单元测试抓到）
   `block_log_format_line` 用 `%S` 输出按键 slug（正确），却用 `%s` 输出 `"pressed"`（错误，宽格式里 `%s` 要 `wchar_t*`）。
   测试里"left 出现"通过、"pressed 出现"失败，正是这个组合的特征。
   **教训**：宽格式串里每个 `%s`/`%S` 都要单独确认实参类型，混用必炸。

3. **`stuck_key.ps1` 一直是"假通过"**（在补日志测试时发现）
   产品**故意忽略注入事件**（`event->is_injected` 直接放行），而该脚本用 `SendInput` 造输入。
   所以它从未真正触发延迟释放，只是验证了"注入点击不会卡键"。
   结论：延迟释放的正确性由 `test_smart_drag.c` 的时序用例覆盖；脚本改为只做"注入输入不卡键"的冒烟，注释已说明，不再宣称覆盖定时器。

### 新增测试覆盖

| 模块 | 断言要点 |
| --- | --- |
| `hook_watchdog` | 基线、空闲、输入+事件、单次怀疑、连续确认、冷却抑制、恢复后再犯、NULL |
| `app_controller` | setter 不落盘、脏标记、延迟提交、连续 setter 只写一次、越界拒绝、写失败保持脏、observers、统计清零回调 |
| `block_log`（内存） | FIFO、满时丢最旧并计数、slug 语言无关、日期/行格式、跨天滚动、参数校验 |
| `block_log`（真实文件） | 建目录+建文件、内容字段、**删目录后下一次写入自动重建**、追加不截断、跨天分文件 |
| 版本一致性 | `APP_VERSION_STRING`、`APP_VERSION_STRING_W`、`MAJOR.MINOR.PATCH` 三者必须一致 |

### 仍然存在的已知限制（本轮未解决，且已知原因）

- **DPI 虚拟化**：项目无 manifest，窗口在 150% 缩放下由系统放大（略模糊）。切 Per-Monitor V2 必须同时改输入框，否则输入框会变小，属独立任务。
- **UIPI**：管理员权限窗口的输入不经过普通权限进程，看门狗会（无害地）误判一次并重装钩子。恢复气泡因此只在首次出现。
- **GUI 无自动化断言**：`e2e.ps1` 只验证"窗口能打开、能关闭、不影响托盘"，视觉效果需人工确认。
- **滑块未实现**：下一轮，届时必须复用 `app_controller_tick` 的防抖提交。

## 审计后的修正（第二轮，实施完成即审）

三个独立视角（新模块正确性 / 钩子时序安全 / 用户可用性）各提出一批问题，以下是**确认成立并已修复**的：

### 高危：钩子内的系统调用与看门狗盲区

| 问题 | 后果 | 修正 |
| --- | --- | --- |
| 钩子回调里 `PostMessage`（日志、气泡）| 消息队列满时 `PostMessage` 有 1 s 超时，远超 300 ms 钩子预算 | 回调只置标志位，由 200 ms 的状态定时器消费；钩子内**零跨进程调用** |
| 看门狗只用光标位移作证据 | 触控板"点一下不移动"永远检测不到死钩子 | 增加 `GetAsyncKeyState` 轮询按钮状态，作为第二路证据 |
| `mouse_hook_init` 不重置 `event_count`；恢复后不重建基线 | 重装后第一次判定必然"健康"，可掩盖再次失败 | `init` 内 `InterlockedExchange` 归零；`RecoverHook` 成功后重新 `hook_watchdog_init` + 采样光标/按钮基线 |
| 每次恢复都弹气泡 | 在管理员窗口里工作会每 30 s 弹一次 | 仅首次恢复提示，其余静默但计数进设置窗口与诊断 |

### 高危：诊断探测污染活钩子

`diagnostics_build` 被设置窗口在**进程内**调用，而它原来走 `mouse_hook_init/install`，
这两个函数会覆盖模块级 `g_manager` → 探测结束后活钩子的回调拿不到 manager，
**整个防护静默失效但仍显示"已启用"**。

修正：新增 `mouse_hook_probe()`，用独立局部钩子 + 独立回调，不触碰 `g_manager`。

### 中危：UI 线程负担

| 问题 | 修正 |
| --- | --- |
| 设置窗口 250 ms 无条件重设文本（`WM_SETTEXT` + 重绘） | 缓存上次文本，**只有变化时才设**；周期放宽到 400 ms |
| 日志一次最多 64 条各 open/write/close，与钩子同线程 | 每次 tick 最多写 16 条，剩余留到下一 tick（`BLOCK_LOG_DRAIN_PER_TICK`） |
| 24 KB 对话框栈缓冲 | 改为文件级 static（仅一个窗口、仅 UI 线程） |

### 用户可用性

| 问题 | 修正 |
| --- | --- |
| 健康鼠标打开窗口看到"0 / 0"，像坏了 | 顶部新增**加粗结论行**"防护正常，正在保护你的鼠标"；空统计改为"鼠标不双击的话这里是空的属于正常" |
| 测试区"拦截 0 次"无解释 | 提示语直接说明"0 次是正常的"；动词改为"看到 / 挡下" |
| 两个开关都叫"记录拦截" | 改为「拦截时弹气泡提示我」/「把拦截记录保存成文件」 |
| "请检查程序目录的写入权限"是开发者语言 | 改为"把程序挪到别的文件夹（比如 D 盘或桌面）再试一次" |

| 恢复次数不可见（静默后无痕迹） | 状态行附加"（被系统打断过 N 次，已自动恢复）" |

### 明确未采纳的建议

- **把自检原文从窗口删掉**：它是用户把问题发给作者的唯一内置通道，删掉会让排查成本回到"让用户开命令行"。保留，但加了"把这段发给作者即可"的说明。
- **日志改成人类可读的中文句子**：会破坏稳定列与 grep，改为一句话表头 + 保持 TSV。
- **把 250 ms 轮询完全改成事件驱动**：计数变化没有现成的推送点（`ObserverSink` 只覆盖设置变更），轮询是合理的，只需去重渲染。

## M5 鼠标体检面板（v1.3.0）

### 为什么改名

原来的窗口叫「设置」，但里面一个能改的东西都没有（只读是 v1.2.0 有意的设计，避免在验证阶段写坏配置）。名字与能力不符，用户会去找"怎么改"，找不到就认为坏了。v1.3.0 起菜单与标题统一叫**鼠标体检**（英文 Mouse check-up）。

### 铁律：判定只有一份

窗口里的「判定」列、"间隔"数字、自检区的证据，**全部来自去抖引擎自己的输出**，界面不做任何 `elapsed <= threshold` 之类的比较。

实现方式：`debounce_process_event_ex()` 在原有函数体里顺手填一个 `DebounceDecision`（原因枚举 + 实测间隔 + 当时的阈值 + 是否推迟松手）。`debounce_process_event()` 退化为它的薄包装，因此两者的判定永远不可能不一致；单测里对同一串事件分别调用两者并比对结果。

原因枚举覆盖了引擎的每个分支：通过、太快、拖拽保护、吞掉松手、滚轮回跳、**推迟松手**、补发松手后通过、程序注入、未启用、零滚动量。窗口只负责把这些枚举翻成当前语言的文字。

### 事件从哪来（关键约束）

被拦下的点击**根本不会到达窗口**，所以动画与日志不能靠 `WM_LBUTTONDOWN` 驱动，必须由钩子的事件流驱动。

- 新增 `src/core/event_trace.c`：128 条定长环形缓冲 + 临界区。钩子回调里只写内存（无分配、无 IO、无 `PostMessage`），窗口在 UI 线程 `pop`。
- **只记录按键/滚轮事件**，不记录移动：移动事件一秒上百条，会在几十毫秒内把有意义的事件挤出去。
- 环形满时覆盖最旧的：用户盯的是刚发生的那一次。
- 窗口每次打开先 `event_trace_clear`，所以不会回放"打开之前"的点击（那些点击的时间戳会早于日志表头，读起来像乱序）。
- 33 ms 的动画定时器同时负责排空缓冲，因此按下到出现日志行的延迟不超过一帧。

### 测试区（涟漪）

- 自绘 `SS_OWNERDRAW` 静态控件，`WM_DRAWITEM` 里画圆环：两个同心环（外 3px、内 1px），颜色按按键区分（左 `#1565C0`、中 `#2E7D32`、右 `#C62828`），600 ms 内半径扩张并向白色淡出，前 120 ms 有一个实心点表示"按下了"。
- 命中判定用**钩子事件里的屏幕坐标**做 `PtInRect`，不是窗口消息：被拦截的点击也能画出圈，这正是用户想确认的那一刻。
- 空闲时在框内画出提示文字（原来独立的提示行删掉，省一行高度）。
- 最多 3 个环，超出时复用最旧的那个槽位，不会溢出数组。
- 定时器只在窗口打开期间运行；环全部消失时再画一帧把残影擦掉，然后 `ripple_view_tick` 返回 false 不再重绘。

### 测试日志与筛选

列：`第N次 | 时间 | 按键 | 间隔ms | 判定`（第一版还有一列「阈值ms」，因右列宽度不足在布局修订中去掉，见文末）。表头是单独的 LTEXT 控件，不随文本滚动。

- 「第N次」是**每个按键自己的**按下计数；松手行沿用所属按下的编号（同一次点击不会变成两行编号）。
- 「间隔」用的是引擎的"距该按键上一次事件"的毫秒数，不是界面自己算的"距上次按下"。第一次事件（或程序注入事件，因为引擎对注入事件不改时间戳）显示 `-`。
- 顶部筛选：`自动`（默认勾选）= 不筛选，三个单选灰掉；取消勾选后回到上次选中的按键，**默认左键**。切换筛选会清空两侧日志并重置编号 —— 视图和内容必须同时切换，否则用户会拿左键的编号去对照右键的行。
- 滚轮事件只属于「自动」视图：三个单选里没有滚轮，强行塞进去反而要解释为什么多一个按钮。

### 列对齐：为什么不用制表位

先按常规做法用 `EM_SETTABSTOPS` + `\t`，实测不可靠：`EM_SETTABSTOPS` 的单位是"平均字符宽度的 1/4"，而中文行里 `间隔（毫秒）` 这种单元格一旦超过制表位宽度，下一个 `\t` 会跳到**再下一个**制表位，列宽就随内容漂移，同一份日志里表格会错位。

改用**定宽字体 + 按显示宽度补空格**：

- 三个文本框统一用 Consolas 9pt（`FIXED_PITCH`）。
- `lang_display_width()` 把全角字符算 2 格、半角算 1 格。实测 Consolas 下 2 个汉字 = 26.40 px，4 个半角字符 = 26.39 px，**正好两倍**，所以补齐后中英混排也能像素级对齐。
- 列宽集中在 `language.c`（6 / 13 / 9 / 7 格），表头与数据行共用同一套 `append_cell()`，天然不会错列。
- 单测锁死三条不变式：任一表头标签不得超出自己的列宽、任一按键名不得超出按键列、任意一行的"判定"必须从同一格开始（中英两种语言、全部 7 个按键都跑一遍）。

### 已拦截的误触

- 上方一行汇总（累计次数 + 有拦截的按键），下方是与测试日志**同一行格式**的文本框，只保留真正的误触按下。
- 过滤规则写在 `is_false_click()`：只认"太快 / 拖拽保护 / 滚轮回跳"。**吞掉的松手**属于同一次误触，**推迟松手**是 Smart Drag 的正常行为，两者都不进这个列表，否则一次误触会被记成两三条。
- 两个文本框都保留系统自带的右键菜单（复制/全选），因此没有另设"复制"按钮。

### 自检区的证据

原来只有 `diagnostics_build()` 的 `key=value` 原文。v1.3.0 在其后追加一段本地化证据：**哪个按键、累计几次、上次与本次的时间、引擎实测的间隔、当时的阈值**。

- 证据由钩子在拦截那一刻写入 `AppState.evidence[]`（纯内存），只在"按下的误触"时写。
- 时间戳是 `GetTickCount64`，快照里同时带回 `now_local` + `now_tick`，窗口据此把 tick 换算成 `HH:MM:SS.mmm`，不需要自己维护时间基准。
- `清零拦截次数` 后计数归零，证据行随之消失（`blocks == 0` 不显示），不会出现"计数 0 但有证据"的自相矛盾。

### 仍然只读

新窗口没有新增任何写入路径：不碰注册表、不碰 `app_controller`、不改阈值。唯一的新增全局状态是 `EventTrace` 与 `evidence[]`，都是纯内存，进程退出即消失。

### 验证

- 单测：2114 项断言（x64 + x86 各跑一遍，0 失败）。新增 `debounce decision`、`event trace ring`、`ripple view`、`check-up formats` 四组。
- 四配置（x64/x86 × Debug/Release）零告警，含 `/analyze`。
- 手工截图验证：中文列对齐、涟漪动画、取消「自动」后单选启用并回到左键、双日志同步清空。
- 版本号同步 `1.3.0`（`version.h` 两处由单测校验一致）。

### 已知限制

- 程序注入的点击会被日志记成「忽略：程序注入」且间隔为 `-`：引擎对注入事件不改时间戳，这是有意的（否则宏/远程桌面会把去抖基准打乱）。
- 窗口打开期间的点击来自整个桌面，不只是测试区；只有落在测试区里的才会画圈。这是刻意保留的：用户可以在真实软件里试，然后回来看日志。
- 日志上限 16 KB 文本（约 200 行），超出后丢最旧的整行。
- 窗口固定尺寸，不支持拉伸；在 1366×768 的小屏上会占掉大部分高度。

### 布局修订：横向 + 只在测试区采集（用户反馈后的第二轮）

第一版是竖排四个分组框，用起来有三个真问题，都是用户当场发现的：

1. **整个窗口的点击都被记进日志**：勾「自动」、点单选框、拖日志滚动条、在日志里选字，全都被记成"点击"。日志因此停不下来地刷新，用户永远看不到中间的内容。
2. **每次都把文本整个重写并滚到底**：想用鼠标拖滚动条看后面的日志，一松手就被下一次刷新弹回底部。
3. **表头写在文本框里**：一滚动表头就跟着滚走，看不出哪一列是什么。

改法：

- **横向两列**：左边测试区分组（`217×198` DLU ≈ 380×371 px，整体 400×420 px），右边自上而下「测试日志」「已拦截的误触」「自检」，四个按钮放在右列底部。窗口 `462×250` DLU ≈ 825×508 px（用户要求的"大概 800×500"）。
- **采集范围**：`EventTrace` 增加 `capture` 矩形 + `capturing` 标志，`event_trace_push()` 先用 `PtInRect` 过滤。窗口在打开、移动、改变大小时把它同步成**测试区画布的屏幕坐标**，关闭时置 `NULL`。钩子回调里只做一次 `PtInRect`（纯内存），不查窗口。
  - 效果：只有白色方框里的点击进日志；勾选框、滚动条、日志文本、按钮、标题栏一律不记。
  - 因为不再被无关点击刷新，滚动位置和选区自然保住；**只有测试区里真的按下时才自动滚到底**，这正是用户要的语义。
- **表头独立**：`IDC_TESTLOG_HDR` / `IDC_BLOCKLOG_HDR` 两个 LTEXT，用同一套等宽字体和同一套补空格的格式化函数（`lang_format_log_header`），滚动时固定可见。
- **列数从 6 减到 5**：`第N次 | 时间 | 按键 | 间隔ms | 判定`。右列只有约 350 px，6 列时"判定"会被挤到换行；按用户最初列的字段取舍，砍掉我自己加的「阈值」列，阈值改由自检区的证据行给出（"间隔 23 毫秒，阈值 50 毫秒"）。英文判定同时缩短成 `block: too fast` / `ignore: no delta` 这种形式，并新增单测保证**任何语言的任何判定都不超过行的剩余宽度**。
- 按钮标签「打开历史记录目录」在 56 DLU 的按钮里放不下，新增短文案 `STR_LOG_DIR_BUTTON`（历史目录 / Log folder），托盘菜单里仍用长版本。

验证：`event trace ring` 新增 8 条断言（窗口未打开时不记录、左/右边界外不记录、移动窗口后旧位置不记录、`clear` 不取消采集、关闭后停止采集）；实测"日志区/滚动条/状态行点击后日志文本完全不变，画布内点击后新增两行"。

### 第三轮：尺寸、任务栏窗口、最新在上（用户第二次反馈）

| 需求 | 做法 |
| --- | --- |

另外两处顺手修正：涟漪半径上限 68 px（测试区变大后圆环会胀满整个画布）；筛选只影响日志内容，**涟漪对任何落在测试区里的按下都画**；发生误触拦截时自动刷新自检区（否则要手动点刷新才能看到新证据）。
